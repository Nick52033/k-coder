# 开发经理评审关注点（来自历史设计文档评论闭环）

> 来源：离职社保欠款测算、一键入职-海外人员、非主动离职管理重构 三份钉钉开发设计文档的评审评论、变更记录与文档修订痕迹归纳。  
> **说明**：钉钉 MCP `get_document_content` **不返回评论正文**，仅含 `comment.contentId` 锚点；生成/更新设计时应结合变更记录、需求评审纪要、代码现状对照本清单。

## 一、开发经理普遍关注的 8 类问题

| 优先级 | 关注点 | 典型评审话术/后果 | 必写章节 |
|--------|--------|-------------------|----------|
| P0 | **需求↔设计可追溯** | 「需求里有报表/导出，设计没写接口」 | 3.1、3.3.1、7.2 |
| P0 | **本期/二期边界** | 「这个功能二期做，别写进本期接口」 | 3.2、3.3.1 备注 |
| P0 | **外部依赖可落地** | 「SAP 什么时候给？谁对接？」 | 3.3.1 负责人列、7.2.2.2 外部接口 |
| **P0** | **2.10 故障分析（FMEA）** | 「2.10 不能全写不涉及」「添加 FMEA 分析」 | **2.10**（见 [fmea-guide.md](fmea-guide.md)） |
| P1 | **事件频率量化** | 「这条规则一天跑几次？」 | 2.8 |
| P1 | **敏感数据安全** | 「工资/证件不能落日志」 | 2.10、特性设计-安全/隐私、6.3 |
| P1 | **现状 vs 目标** | 「原来怎么做的？改哪不改哪？」 | 3.3.x 设计细节首段 |
| P2 | **架构/效益说明** | 「重构为了什么？省多少人天？」 | 1.2、2.1、3.1（重构类需求） |

## 二、按文档类型的附加检查

### 2.1 集成/测算类（如 paypro-platform-be）

- [ ] 需求中**每个用户可见能力**（列表、导出、重试、对账、通知）在 **3.3.1 有一行、7.2.2 有一节**；评审后漏项用变更记录闭环（例：v1.1 补充「欠款明细报表列表查询与导出」）。
- [ ] **2.8** 写清：定时任务（cron/日终）、实时触发、批跑补偿、失败重试次数与告警对象。
- [ ] **2.10** 覆盖：规则/配置错误、外部接口超时、**敏感数据泄露**、金额计算错误；高风险项写「事前/事中/事后」控制与上线前复核项。
- [ ] **3.2** 明确「本期不包含」：如财务回款标识、批量标识回款、动态追踪等，避免与 3.3.1 矛盾。
- [ ] 外部依赖行标注：**接口名称、提供方、复用/新建、预计就绪时间**（如「约 5 月 15 日提供」）、Mock/桩策略。
- [ ] **7.2.1** 错误码按模块分子节（配置/引擎/对账/报表等），与 3.3.1 模块一致。

### 2.2 规则增强/遗留 WebForms（如 ipsa-rra）

- [ ] **禁止过度设计**：生成前检索代码；已有能力（字典项、SAP 同步链路）写「**已实现/沿用**」，勿重复列为待开发（评审常标「不需要修改」）。
- [ ] 每个规则变更写 **现状 → 目标 → 影响范围**（例：大陆员工流程不变；仅海外/港澳台触发新分支）。
- [ ] **2.7** 写触发条件（例：「非收费 + 离职补缺=是」才增强校验）。
- [ ] **3.3.x 设计细节**落到具体文件（`EnterApply.ascx.cs`、`OverseasEntryRuleHelper.cs` 等）与方法名。
- [ ] 联动规则单列：国籍↔证件类型、心理测评跳过、背调简化（仅岗位需求）各自写触发时机与 UI 行为（隐藏/跳过/日志）。
- [ ] **2.10** 含 SAP 新码（E1/E2）未配置、正则误杀、国籍误判等行。
- [ ] .NET 3.5 项目：特性设计或 3.3 备注 **编码/BOM、BCL 引用** 风险（见项目 docs/lessons）。

### 2.3 重构/迁移类（如 employment-relation-be）

- [ ] **1.2** 含痛点量化（处理时长、人天、成本）与 **1.2/3.1 效益目标**（评审常要求「补充效益数据」）。
- [ ] **2.1/1.3** 旧架构 vs 新架构对比表：Workflow→BPM、系统合并、权限体系统一。
- [ ] **SAP 离职原因/单据类型** 对齐写清映射策略与字典来源。
- [ ] **已实现 vs 二期**：电子填表、特殊离职证明模版、额外通知书等标注「二期」。
- [ ] 流程类：**批量审批上限**（如 ≤10）、加急支付通道（短信/钉钉）、BPM 节点与表单 ID。
- [ ] 支付/银行/印章/纠纷系统：**7.2.2 外部接口** + 失败告警 + 操作审计。
- [ ] 附件与隐私：预览方式、权限、脱敏字段列表。

## 三、生成前必做（Agent 执行）

在 **§4 生成设计正文** 之前，完成以下步骤并写入 `_需求摘要.md` 或内部核对表（可选输出给用户）：

1. **需求条目清单**：从需求文档提取功能编号/标题 → 映射到 3.3.1 行号（未映射标「待确认」）。
2. **代码现状扫描**：在 `D:\ProjectCode\{项目}` 检索相关 Controller/Service/Page；已存在实现标「已实现」，仅增量标「待开发」。
3. **外部依赖登记表**：系统名、接口、负责人、时间、Mock 策略。
4. **FMEA 草稿**：按 [fmea-guide.md](fmea-guide.md) 从 3.3.1 模块 + 外部依赖 + 敏感数据/金额 列失效模式清单（生成 2.10 前必做）。
5. **范围剪刀**：需求「本期不做/二期」→ 3.2 与 3.3.1 备注一致。
6. **评审关注点预选**：按本章第二节选对应模板勾选。

## 四、生成后质量门禁（对照开发经理视角）

输出前逐项自检；任一项不通过则补写后再落盘/写钉钉：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 3.3.1 ↔ 7.2 | 3.3.1 每个「接口/服务名称」在 7.2.2 有对应条目（外部接口可入 7.2.2.2） |
| 2 | 需求覆盖 | 需求功能概述每条在 3.1 或 3.3.1 出现；无孤儿需求句 |
| 3 | 2.8 | ≥3 行事件，含触发频率（次/日/月/定时） |
| **4** | **2.10 故障分析** | **表体行数 ≥ max(3, 3.3.1 模块数)；每外部依赖≥1 行；敏感/金额有专项行；S/F/D 填 1～5；总结段≥2 段（风险主线 + 事前事中事后）。细则 [fmea-guide.md](fmea-guide.md)** |
| 5 | 3.2 | 显式「本期不包含」「二期」 |
| 6 | 外部依赖 | 3.3.1 外部行有负责人或「待确认：对接人」 |
| 7 | 现状目标 | 每个 3.3.x 设计细节首段 1～3 句说明改什么、不改什么 |
| 8 | 过度设计 | 无「代码已存在仍标待开发」项 |
| 9 | 变更记录 | 若为更新：变更说明写清本次响应的评审项（非仅「更新」） |
| 10 | 待确认项 | 输出表格列出所有「待确认：xxx」 |

## 五、更新已有设计时（响应评论）

用户或评审提供 **已有设计 nodeId** 时：

1. `get_document_content` 读取当前正文 + 本地同名 md  diff。
2. 从**变更记录**、用户粘贴的评论、需求 v1.1 增量反推修改范围。
3. 仅修改被点名的章节；**变更记录新增一行**，说明对应评审意见（例：「补充欠款明细报表列表查询与导出接口设计（3.3.4 / 7.2.2）」）。
4. 块级更新钉钉；禁止 overwrite 整篇。
