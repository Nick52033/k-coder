### 已确认可复用的干净接缝（关键证据）
- `src-tauri/src/mobile/rpc.rs:329` — `dispatch(&GatewayContext, &Arc<Mutex<RpcSession>>, RpcRequest) -> Option<RpcResponse>` 完全与传输层解耦，不出现 axum/socket 类型。中继连接可直接复用。

### 需要新写的部分
1. 出站 WSS 客户端 + 20s 心跳 + 三次失败退避重连 + 在线状态机。
2. 设备非对称密钥与挑战响应。**注意：现有 `auth.rs` 是对称模型**（`random_token(32)` + SHA-256 摘要落盘 + 内存访问令牌），与设计的设备密钥对是两套模型，不是小改。

4. 中继服务本身（部署/域名/证书/监控/故障预算）。
5. 离线行为：有界待投递队列、只缓存控制类消息、电脑离线期间不接受新移动会话。
6. 两种模式共存的设置页与能力策略（异地默认更窄、破坏性操作要求桌面端确认）。

## 补充：中继为何必须公网可达，以及现有网关主动封堵的四道闸

柯工追问「中继为什么要云主机」。澄清结论：**不是必须有云主机，而是必须有一个双方都能主动出站的、公网可达的固定地址**；云 VPS 只是最常见形态，Cloudflare Workers/Durable Objects（无服务器、自带 TLS 与域名、运维最轻）也满足。

### 现有网关在四处主动拒绝公网暴露与隧道（已逐条核对 `server.rs`）
| 位置 | 行为 |
| --- | --- |
| `is_allowed_source`（:118） | 只认 loopback / private / link_local / ULA；公网来源 → 403 |
| `host_header_is_allowed`（:141） | `Host` 必须是 `localhost` 或**私网 IP 字面量**；传域名时 `parse::<IpAddr>()` 失败 → 直接 false，**用域名指过来也会被拒** |
| `has_forwarding_headers`（:157） | 六个转发头（`x-forwarded-for/-host/-proto`、`x-real-ip`、`forwarded`、`via`）任一存在 → 400。任何加这些头的反代/隧道都过不去 |
| `resolve_bind_ip`（:172） | 绑定地址只能是回环或私网，想绑公网网卡都不允许 |

结论：**「用 Cloudflare Tunnel / FRP 把 8787 捅出去」在代码层面走不通**——不是遗漏，是故意堵的。这正是设计文档 §9 阶段 C 写「不得通过直接暴露方案 1 的端口实现方案 2」的落地依据。

### 重要实测发现：Tailscale 路径同样会被拒
`rustc` 实测确认（Rust 1.9x，`is_shared()` 尚为 unstable，不可用）：

```
100.64.0.1       is_private=false is_link_local=false is_loopback=false
100.101.102.103  is_private=false is_link_local=false is_loopback=false
10.0.0.5         is_private=true
192.168.0.220    is_private=true
169.254.1.1      is_link_local=true
1.1.1.1          is_private=false
```

Tailscale / ZeroTier 使用的 CGNAT 段 `100.64.0.0/10` **不在 Rust `Ipv4Addr::is_private()` 范围内**，因此 `is_allowed_source` 会拒绝 Tailscale 地址。若将来要让「不自己搭中继」的 Tailscale 路线可行，需在 `is_allowed_source` 里显式放行 `100.64.0.0/10`（并可考虑用 `is_shared()`，但要等其稳定）——这是一处**尚未决定是否要开的口子**，改动会影响 `host_header_is_allowed` 与 `resolve_bind_ip` 的连带语义，需一并评估。

### 本轮踩到的坑（可复用）

1. **`Edit` 成功但被外部进程回写覆盖**：改 `src-tauri/src/app_state.rs` 与 `src-tauri/src/commands/mod.rs` 时各出现一次「工具报成功、`cargo check` 却报字段/导入缺失」，`grep` 确认编辑确实没落盘（同一时段还遇到一次 `EBUSY: resource busy or locked` 与一次 `target/debug/.fingerprint/... 拒绝访问 (os error 5)`）。**对策：每次编辑后立刻 `grep` 复核关键行，再编译**；不要连做十几次编辑后才第一次编译。
2. **维护/扫描类 keyset 分页必须选一个「自己不会改写」的排序列**：`expire_due` 会写 `updated_at_ms`，所以分页只能按 `id`（`list_active_by_id`）；若按 `updated_at_ms` 分页会跳行。
3. **`MemoryService::list` 是按 scope 的 keyset 分页，枚举不了全部 scope**：需要「跨 scope 的有界快照」时必须新增仓储查询（本次加了 `list_recent_active`），别试图在领域层循环 scope。
4. **要造「重复 key」或「已过 TTL」的行，只能走 `MemoryRepository::append` 直写**：`upsert` 会因 `(scope, key, revision)` 唯一索引拒绝同 revision，也会因 `expiresAtMs must be in the future` 拒绝过去时间；测试夹具统一用 `MemoryRepository::append` + 显式 `created_at_ms`。
5. **「无工具 Turn」的正确形状是空注册表 + `AllowRegisteredTools`**，不是写一份全拒绝的 denylist：没有注册就没有可授权的工具，天然封闭，也不会随工具清单演进漏掉新工具。
6. **`ToolRegistry::new_with_policy` 需要 `Arc<dyn PolicyEngine>`**，`AllowRegisteredTools` 是零字段单元结构，直接 `Arc::new(AllowRegisteredTools)`。
7. **`TauriEventPublisher` 是 `commands/mod.rs` 的私有类型**：想让 `lib.rs` 复用调度逻辑，就把整个 `spawn_*_scheduler` 放在 `commands/mod.rs` 里 `pub` 出来，而不是在 `lib.rs` 里重建发布器。
8. **Tauri 命令名 = 函数名**：把命令体抽成可测的 `pub(crate)` 辅助函数时，别顺手把辅助函数命名成 `*_command`（会改掉前端要调的 IPC 名）；辅助函数换个名字（本次 `accept_memory_maintenance_disclosure` 命令 + `record_memory_maintenance_disclosure` 辅助）。

## 自建中继的两条路径（柯工追问「自己搭中继怎么搭」）

### 关键发现：自建 WireGuard 中继可零 Rust 改动跑通方案 1
用 `10.8.0.0/24` 而不是 Tailscale 的 `100.64.0.0/10`，现有四道闸**全部放行**（已逐条核对 `server.rs`）：

| 闸口 | `10.8.0.2` 结果 |
| --- | --- |
| `is_allowed_source`（:118） | `10.x` → `is_private=true` ✓ |
| `host_header_is_allowed`（:141） | `Host: 10.8.0.2:8787` 解析为 IP → 私网 → ✓ |
| `has_forwarding_headers`（:157） | WireGuard 是三层隧道，不加 HTTP 头 ✓ |
| `resolve_bind_ip`（:172） | 绑定 `10.8.0.2` 属私网 ✓ |

TLS 也自动满足：`tls.rs:104` `load_or_create_identity(data_root, ip)` → `generate_self_signed` 用 `CertificateParams::new(vec![host])`，rcgen 对 IP 字面量生成 IP SAN。**同一条代码路径已被原生验收证明可行**（真实 `192.168.0.220` 上 TLS 握手成功、指纹逐位一致、手机协议客户端连通），WireGuard 路线唯一新增变量是 WireGuard 本身能否投递包，与 k-Coder 代码无关。

拓扑：`手机 ──WG──> VPS(WireGuard 服务端) <──WG── 电脑`，手机访问 `https://10.8.0.2:8787/m/`。VPS 只看到加密的 WG 包，看不到内部 TLS 流量。

代价：手机须常装并开启 VPN 客户端；流量绕路 VPS 增加延迟；电脑侧 WG 断开即不可用；绑定 IP 变化会重新生成证书导致指纹改变，手机需重新核对。

### 应用层中继（方案 2 原设计）的最简形态
中继侧职责仅四件：识别两端身份、配对、转发不透明帧、离线有界队列。建议 Cloudflare Workers + Durable Objects（一个 DO 实例 = 一台电脑，持有该电脑的 WS 与该电脑所有手机的 WS），免费额度够个人用，自带 TLS 与域名、无进程与证书运维。

```
电脑 --WSS--> wss://relay/host    (hostId + 签名)
手机 --WSS--> wss://relay/device  (deviceId + hostId + 签名)
中继：手机帧 → 查 deviceId→hostId → 原样转发给对应电脑连接
      电脑帧 → 查已配对设备 → 广播给该电脑的所有手机连接
```
中继完全不解密，符合设计 §6.4「拒绝任意代理 HTTP、任意转发目标、客户端指定转发目标」。

### 根因（已用独立最小 crate 完整复现并证明）
`tauri::test` 的 mock runtime 会把窗口层链进测试二进制 → 经 `tauri-plugin-dialog` → `rfd` 导入 `comctl32.dll!TaskDialogIndirect`（Common Controls **v6 专有**导出）。lib 测试二进制没有 v6 清单声明时，加载器把它解析到 System32 的 v5.82，报 `STATUS_ENTRYPOINT_NOT_FOUND`（`0xc0000139`），进程在跑任何用例之前就死掉（表现为 `cargo test --lib` 无输出直接失败）。仓库里所有 `k_coder_lib-*.exe` 的 `manifestVersion` 计数都是 0。

### 四条硬约束（都是实测结论，不是推测）
1. **`cargo:rustc-link-arg-tests` 不覆盖 lib 单元测试**。它对只有 lib 的包直接报 `The package ... does not have a test target`；只作用于 `tests/*.rs` 集成测试。覆盖 lib 单元测试的唯一作用域是 `cargo:rustc-link-arg`。
2. **`rustc-link-arg` 会同时作用于 bin**，而应用清单由 `tauri_build` 经 `tauri-winres` → `embed-resource` 的 `cargo:rustc-link-arg-bins` 注入（`embed-resource-3.0.11/src/lib.rs:443`）。两者叠加可能冲突，所以必须做成可选。
3. **清单文件必须纯 ASCII**。`mt.exe` 不按 XML 声明里的 `encoding="UTF-8"` 解析，而按 ANSI 代码页；出现中文会报「无法分析请求的 XML 数据」并以 `LNK1327` 失败。纯 ASCII 注释可正常解析。
4. `tauri-build` 的默认应用清单（`windows-app-manifest.xml`）本来就带 Common Controls v6，所以**应用本身一直没问题**，只有测试目标漏了。

- `src-tauri/build.rs`：仅当 `CARGO_FEATURE_MOCK_RUNTIME_TESTS` 存在时，发出 `cargo:rustc-link-arg=/MANIFEST:EMBED` 与 `/MANIFESTINPUT:<abs>`。
