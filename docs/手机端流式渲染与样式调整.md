# 手机端流式渲染与样式调整

对应 `P10-188`（手机远程控制方案 1）的真机反馈：手机端页面「没有流式输出，一次性全部出的」，同时布局与样式需要调整。本文记录排查过程、改了什么、怎么验证，以及仍未验证的部分。

## 1. 排查：先确定问题在哪一层

手机端只有三层可能出问题：Provider/网关是否真的推送了分片、传输层是否真的把分片投递到这条 WebSocket、页面是否真的按分片渲染。前两层已有自动化覆盖（`src-tauri/tests/mobile_turn_lifecycle.rs` 的 (a) 组断言 `turn_started` → 3 个 `text_delta` → `turn_completed` 逐帧到达；`src-tauri/src/mobile/events.rs` 把 `TextDelta` 路由为可下发），因此先把页面这一层单独拎出来验证。

做法是**用假 WebSocket 把真实页面跑起来**：Playwright 的 `page.routeWebSocket` 顶替网关，按服务端真实帧形状注入事件，观察 `#timeline` 的渲染结果。结论有两条：

1. **分片是逐条渲染的**（`我先` → `我先确认当前` → … 每次都可见），所以「看不到流式」不是页面不渲染分片。
2. **`turn_completed` 到达后，刚流出来的正文会被整段清空**。原因是旧实现把分片文本放在独立的 `state.deltas` 里，`turn_completed` 先把终态消息追加进同一个 map，紧接着 `finishTurn` 又 `state.deltas.clear()`，于是正文在 Turn 收尾那一刻消失，只剩「工具活动」卡片——用户必须重新进入会话（触发一次 `thread/read` 快照）才能重新看到这段话，看起来就像「一次性全部蹦出来」。

同一次排查还暴露了三个同源缺陷：

- 分片气泡被渲染在**所有快照条目之后**，与它在 Turn 里的真实位置无关；长会话里读起来是错位的。
- 每个分片都会 `timeline.textContent = ""` **整屏重建**，手机上既费电又看不出「正在生成」。
- 页面没有任何跟随滚动，也不做连接保活：手机切后台/锁屏后 WebSocket 会静默失效，回来时只能靠一次整段重读，观感同样是「一次性出现」。

## 2. 改了什么

改动集中在 `src-tauri/src/mobile/assets/mobile.html`（单文件内联资产，无构建步骤）。

### 2.1 时间线模型：条目化 + 增量渲染

时间线改成一串有序条目，每条有稳定 key：

| 条目 | key | 说明 |
| --- | --- | --- |
| 用户/助手消息 | `item:<itemId>` | 快照与增量用同一个 item id，因此不会重复 |
| 工具卡片 | `tool:<callId>` | 快照投影里带 `callId`，与增量天然对齐 |
| 文件变更 | `change:<changeId>` | |
| 任务清单 | `todos` | |

渲染只在 key 对应的节点上做增量修改：正文续写走 `appendChild(createTextNode(...))`，DOM 里只追加一个文本节点（节点本身不重建）；批量更新用 `requestAnimationFrame` 合并。`applyText` 会比对「已写进 DOM 的内容」与模型，前缀相同就追加、不同才整体替换——所以 `tool_output_delta` 的命令输出同样是续写。

### 2.2 Turn 收尾不再丢正文

`turn_completed` 的终态消息现在是**权威版本**：只在它与已流出的文本不一致时覆盖同一条气泡；`finishTurn` 只清流式标记，不再清文本。Turn 结束后 1.2 秒会静默重读一次会话（此时后端的持久化已完成），把手机端与桌面端对齐，并按条目身份合并——快照里已经有的条目以快照为准，正在生成、尚未落盘的条目保留本地内容。

### 2.3 连接保活与手动刷新

- 25 秒心跳（`ping`），80 秒没有收到任何服务端消息即判定连接已死并重连，不再等用户手动刷新。
- `visibilitychange` 回到前台时：连接不是 OPEN 或已超时就重连，否则补一次心跳并按需静默重读会话。
- 会话工具条新增 `↻`：任何时候都能手动重读当前会话。

需要说清楚的边界：服务端的 `deliverySeq` 是**按连接**递增的，重连后旧游标必然失效，所以重连后仍然要走一次 `thread/read` 快照。**页面被系统挂起期间不可能继续收到分片**，那段时间的内容只能靠快照补上——这是设计使然，不是本次能消除的。

### 2.4 样式

- 输入区改成单行：输入框自适应高度（空草稿交回 CSS 行高，最多 132px），右侧按钮在「发送/停止」之间切换，底部按 `env(safe-area-inset-bottom)` 让位。真实测量输入区高度写入 `--composer-h`，正文区按它留白，避免最后一条消息被输入框永久压住。
- 会话工具条与顶部栏吸顶，偏移量按实测高度写进 `--header-h`；工具条用不透明背景（此前的渐隐会让滚动中的长文本透出来）。
- 气泡左右分栏（用户靠右、助手靠左），助手气泡在流式中带光标；工具卡片折叠为 `<details>`，摘要显示「动作 + 状态」，失败保持展开可读；命令输出用等宽字体并限高滚动。
- 任务清单带 ☐/◐/☑ 标记；审批与提问卡片固定在时间线最前面，不会被后来的长正文顶走。
- 空壳气泡（快照里的 `event` 条目等）不再渲染。

## 3. 验证

新增浏览器回归 `e2e/mobile-stream.spec.ts`（desktop + narrow 双视口 8 项全绿），用假 WebSocket 驱动真实页面：

| 用例 | 断言 |
| --- | --- |
| 分片逐条呈现 | 每次注入一个分片后立即断言气泡文本等于前 n 个分片拼接；并断言气泡节点在续写后仍是**同一个** DOM 节点（`data-probe` 仍在），证明不是整屏重建 |
| Turn 结束不丢正文 | `turn_completed` 后正文仍在且只有一条；随后的静默重读（快照已含该消息）不会产生第二条 |
| 快照与增量按身份合并 | 同一条用户消息、同一个 `callId` 的工具卡片在重读后都只保留一份；工具卡片状态从「运行中」变「完成」且输出可见 |
| 输入区让位 | `--composer-h` 被真实测量，正文区底部留白与输入区高度一致（±40px），发送按钮可达 |

既有用例同时回归：`e2e/mobile-settings.spec.ts` 双视口 2 通过。

质量门槛：`pnpm build`（`tsc` + `vite build`）通过；`cargo fmt --check` 通过；`cargo check --all-targets` 通过（覆盖包括上述集成测试在内的全部目标）；`cargo test --lib mobile::` 78 通过 / 0 失败。

### 3.1 本轮未能执行的部分

`src-tauri/tests/` 下三个移动集成目标（`mobile_gateway`、`mobile_dto_contract`、`mobile_turn_lifecycle`）本轮**没有跑成**，卡在链接而不是断言：

1. 客户端正在从 `D:\code\k-coder\src-tauri\target\debug\k-coder.exe` 运行（PID 17268，就是手机连着的那个进程），cargo 为集成测试目标重建应用二进制时无法删除被占用的文件（`拒绝访问 os error 5`）。
2. 临时移开 bin 目标绕开后，测试二进制改用另一种方式失败：`CVTRES : fatal error CVT1100: 资源重复。类型: MANIFEST` → `LINK : fatal error LNK1123`。原因是 `build.rs` 无条件发出的 `cargo:rustc-link-arg-tests=/MANIFEST:EMBED` + `/MANIFESTINPUT:windows/tests.manifest` 与 `tauri_build` 生成的 `resource.lib`（其中已含 RT_MANIFEST 资源）冲突。这条与本次改动无关——改动只涉及 `mobile.html`（`include_str!` 资源）、新增的 `e2e/mobile-stream.spec.ts` 与文档，不改变任何链接参数——属于当前工作区既有构建图问题，需要单独排查（例如把 `-tests` 的清单注入改成只在缺少 `resource.lib` 时生效，或改用 `tauri_build` 同一个资源通道）。

受影响的两个断言已按内容人工核对：`mobile_gateway.rs` 的 `mobile_page_is_served_without_external_assets` 要求页面包含 `k-Coder` 与 `pair`，新页面分别命中 7 处与 50 行，且没有任何外部资源引用（`src`/`href` 指向 http(s) 的引用为 0）。


## 4. 仍未验证的部分

1. **真实手机 + 真实 Provider**。本次验证用的是真实 Chromium（移动视口与 UA）与假 WebSocket，证明的是页面在收到分片时**确实逐条渲染**；没有覆盖真机的锁屏/切后台时机、iOS Safari 对自签证书的处理，也没有覆盖真实 Provider 的分片节奏（上游中转把整个响应缓冲后一次性吐出时，手机端与桌面端同样只能「一次性」收到）。
2. **切后台期间的内容**只能靠重连后的快照补齐，页面不会也不可能在那段时间继续渲染分片。
3. **未部署到 `D:\apps\k-coder\`**：安装目录里的客户端仍是旧页面，需要重新构建部署后才能在手机上看到本次改动。
