# **1、 设计概述**

## **1.1 运行环境**

| 序号 | 项目 | 详细信息 |
|------|------|------------|
| 1 | 后端软件环境 | Rust 2024；Tauri 2；沿用 AgentRuntime、ToolRegistry、PolicyEngine、ThreadRepository |
| 2 | 前端软件环境 | React、TypeScript、Vite、Zustand；沿用现有设置页、工作台和事件投影 |
| 3 | 中间件 | 不引入 PostgreSQL、pgvector、Redis、Elasticsearch、独立向量数据库或常驻检索服务；仅按用户开关调用固定的硅基流动 HTTPS embedding 接口 |
| 4 | 数据库 | 现有 k-coder.db（SQLite bundled）；新增知识库表、SQLite FTS5 虚拟表和 embedding 向量 BLOB 表 |
| 5 | 文件存储 | runtime-data/knowledge/events.jsonl 保存事实事件；工作区来源保存相对路径、文件指纹、分块文本和版本化向量，不复制工作区文件 |
| 6 | 网络 | 仅在用户启用语义检索且配置凭据时访问官方 `https://api.siliconflow.cn/v1/embeddings`；请求正文仅包含用户明确选择来源的有界 chunk 或当前 query，不上传 API Key 或绝对路径 |
| 7 | 平台 | Windows、macOS、Linux；文件路径和链接逃逸复用现有工作区安全边界 |

## **1.2 需求背景**

需求来源：本次对话（2026-08-31），用户先要求低成本落地，后续指定使用硅基流动的免费/低成本 embedding 服务和 BGE-M3 模型。

**业务背景（摘要）：**

k-Coder 已有用户记忆、工作区词法搜索和有界文档解析能力，但三者分别服务于用户偏好、即时文件定位和一次性附件提取。现有仓库搜索每次查询重新扫描文件，检索结果缺少稳定 revision 和引用身份；如果直接把整份文档放入上下文，会增加上下文消耗，且无法在回答中可靠回到原文位置。用户熟悉“文本切片后入库”的模式，希望在不引入 PostgreSQL/向量数据库的前提下，用硅基流动 BGE-M3 补充语义召回，并保留本地词法检索作为低成本和故障降级路径。

**本期目标（摘要）：**

建立一个本地优先、可重建的知识库。第一期只支持工作区内已确认的文本类来源，使用有界结构化切片，同时生成 SQLite FTS5/BM25 词法索引和可选的 BGE-M3 向量；模型通过只读 `search_knowledge` 工具按需查询，结果带 citationId、相对路径和行区间。索引按文件 SHA-256、解析/切片版本和 embedding 模型版本增量更新，索引任务可取消、可恢复。硅基流动不可用、没有 API Key、被限流或用户关闭语义检索时，自动降级为 FTS-only，不影响普通对话。向量数据库、远程共享知识库和第二种 embedding 服务不属于本期。

## **1.3  架构设计方案**

**系统架构概要：**

知识库作为独立 knowledge 领域接入现有运行时，不扩展 advanced/memory.rs，不在 Tauri 命令中写 SQL，不在 KnowledgeService 中实现第二套智能体循环。第一期数据流如下：

~~~text
用户选择工作区文件
        │
        ▼
Knowledge Commands ──> KnowledgeService
                             │
                  ┌───────────┼───────────────┐
                  ▼           ▼               ▼
              SourceManager  Parser        Indexer
                  │           │               │
                  ▼           ▼               ▼
           file hash/locator  Chunker   FTS5 + BGE-M3
                                                  │
                              ┌───────────────────┘
                              ▼
                         Hybrid Retriever
                              │
                              ▼
                       Citation / Snapshot
                                   │
                                   ▼
                             AgentRuntime
                                   │
                                   ▼
                         Chat Provider 请求
~~~

**核心技术栈：**

- Rust 负责来源校验、解析调度、结构化切片、SQLite 事务、embedding HTTP 调用、向量归一化/余弦计算、引用快照和取消；复用现有 `reqwest`，不新增本地模型文件。
- SQLite FTS5 保存确定性的词法索引；为了兼顾中文和代码标识，写入索引前生成规范化词项：英文统一小写，拆分 camelCase、snake_case、路径和常见符号；中文生成有界二字词，同时保留原文用于引用。
- BGE-M3 由硅基流动托管。第一期固定能力 profile 为 `provider=siliconflow`、`endpoint=https://api.siliconflow.cn/v1/embeddings`、`model=BAAI/bge-m3`、`encoding_format=float`；向量维度以响应数组长度为准。只有用户显式开启语义检索并配置 API Key 时才发送 chunk/查询文本。
- 向量以版本化 little-endian `f32` BLOB 保存在本地 SQLite，由 Rust 以有界批次计算 cosine；第一期不引入 pgvector、HNSW 或常驻向量服务。
- AgentRuntime 只接收已经通过 scope 和 revision 过滤的检索快照；不读取数据库、不接受模型提交的绝对路径、不由模型决定权限。
- React 只显示集合、来源、索引状态、检索活动和引用；持久化知识状态由后端负责。

# **2、 总体方案**

## **2.1 技术方案**

**开发语言：** Rust 2024、TypeScript。

**技术框架：** Tauri 2 + React/Vite；沿用 AgentRuntime、ContextBudget、ToolRegistry、PolicyEngine、JsonlThreadRepository 和 rusqlite bundled SQLite。

**关联服务：**

1. 工作区文件系统：复用 workbench 的路径规范化、文件元数据读取和符号链接/junction 逃逸拒绝。
2. 文档解析：第一期只接入现有纯文本解析路径，包含 Markdown、TXT、JSON、YAML、TOML、XML、HTML、CSS、JS/TS、Rust、Python、C#、Java、SQL、Shell 等已支持文本扩展名。
3. SQLite FTS5：在现有 k-coder.db 中保存可重建的 chunk 投影和倒排索引。
4. 硅基流动 Embeddings API：使用 `POST https://api.siliconflow.cn/v1/embeddings`，请求头为 `Authorization: Bearer <API Key>` 和 `Content-Type: application/json`；第一期固定 `model=BAAI/bge-m3`，不允许调用方覆盖模型或 endpoint。
5. 本地向量存储：向量以归一化 little-endian `f32` BLOB 保存于 SQLite，由 Rust 读取并计算余弦相似度；不引入 PostgreSQL/pgvector、HNSW 或额外向量服务。
6. AgentRuntime：通过一个混合检索工具和一个 citation 读取工具使用知识库；管理来源、embedding 配置和刷新索引只能由用户介导的 Tauri 命令执行。

## **2.2 存储方案**

| **类型** | **说明** | 用途 |
|----------|----------|------|
| runtime-data/knowledge/events.jsonl | 集合启停、来源添加/删除、索引任务和 active revision 切换的追加式事实事件 | 崩溃恢复和审计 |
| k-coder.db knowledge_collections | 集合 ID、名称、scope、enabled 和时间 | 设置页列表和权限过滤 |
| k-coder.db knowledge_sources | 工作区身份、相对路径、文件大小、修改时间、SHA-256、active embedding profile 和状态 | 增量判断和来源展示 |
| k-coder.db knowledge_revisions | parser/chunker 版本、内容指纹、active 标记和切片统计 | 代际切换和回滚 |
| k-coder.db knowledge_chunks | chunk 文本、规范化 terms、ordinal、token 估算和 locator JSON | 引用读取和 FTS 外的元数据查询 |
| k-coder.db knowledge_chunks_fts | FTS5 内容表，索引 title、path、terms 和正文 | BM25 词法检索 |
| k-coder.db knowledge_chunk_embeddings | chunk 对应的 provider/model、维度、归一化向量 BLOB 和状态 | BGE-M3 语义检索；可按模型版本重建 |
| k-coder.db knowledge_index_jobs | queued/running/succeeded/failed/cancelled 状态、进度和错误码 | 索引任务恢复和 UI 进度 |
| k-coder.db settings | embedding.enabled、batchSize、timeout、scan cap 等非敏感配置；provider/endpoint/model/profile 为只读能力事实 | 语义检索开关和运行参数 |
| 操作系统凭据存储 | `embedding-api-key:siliconflow` | 保存硅基流动 API Key；SQLite、JSONL 和日志不保存密钥 |

知识库仍不复制工作区文件，但会在用户明确启用语义检索后把选定 chunk 的有界文本发送到硅基流动，并将返回向量保存在本地。向量 BLOB 使用 `f32`、维度上限 4,096、单条大小上限 16 KiB；写入前检查维度、有限数值和固定模型 profile。API Key 只进入操作系统凭据存储，绝不写入 SQLite、JSONL、Provider 历史或日志。工作区文件变更后，下一次刷新按文件 hash、parser/chunker 版本和固定 embedding profile 生成新 revision；旧 revision 在新 revision 成功切换后按保留策略清理。

**第一期模型约束：** 用户指定的是 BGE-M3，采用硅基流动模型 ID `BAAI/bge-m3`。endpoint、model 和 `encoding_format` 由后端能力 profile 固定，设置页只展示，不接受任意替换；BGE-M3 请求不得发送 `dimensions`。用户提供的 `Qwen/Qwen3-VL-Embedding-8B` 是另一种支持文本/图片混合输入的 VL Embedding 模型，本期不接入，也不能与 BGE-M3 的向量、输入限制或 revision 混用。未来若支持其他模型，必须新增独立能力 profile、迁移和评测，不得复用本期向量。

**迁移约定：** 已有 SQLite 数据库升级时，为 `knowledge_revisions` 和 `knowledge_sources` 增加 `embedding_encoding_format`/`active_embedding_encoding_format`，默认值为 `float`；历史 revision 按 `embedding_provider=none`、无向量的 `lexical_only` 兼容读取，不回填或伪造 embedding。`knowledge_chunk_embeddings` 为空表创建，FTS 投影和知识事件可按现有重建流程生成。迁移失败必须关闭知识库命令，不得删除既有会话或工作区文件。

## **2.3 消息队列**（可选）

不引入外部消息队列。索引刷新使用 Tokio 有界任务队列：

- 每个 sourceId 同时最多一个 running 任务；重复刷新合并为一次 pending refresh。
- 解析和本地 FTS 写入在 spawn_blocking 中执行；embedding 请求由异步 `reqwest` 客户端按 8～16 个 chunk 一批发送，每批后检查 CancellationToken。
- 同一固定 embedding endpoint 默认最多 1 个并发请求；429/503/504 和可判定的网络超时最多做 2 次指数退避重试，400/401/403/404 及响应结构错误不重试。每批响应必须检查 `data[].index` 连续性、向量维度和 finite 值。
- 任务状态先写入 SQLite/事件，再发布 UI 进度。应用退出时 running 任务恢复为 queued 或 failed，不能直接显示成功；已完成 FTS 但尚未取得向量的候选 revision 标记 `embedding_pending`，不伪造语义索引成功，用户下一次刷新可重试。
- 队列容量、来源数量、单文件字节数、单次提取字节数和任务墙钟时间均有限制。
- AgentRuntime Turn 与索引任务使用独立取消令牌；删除来源时先阻止新查询，再取消任务并清理 active 投影。

## **2.4 系统交互**

用户在设置页启用知识库后创建 Collection，选择当前工作区中的一个或多个精确文件。后端检查文件是否为普通文件、是否仍位于当前规范化工作区、扩展名是否受支持以及大小是否在限制内。通过校验后追加来源事件并排队索引，UI 显示 queued/running 状态。

索引任务读取文件并计算 SHA-256。若文件指纹、解析器版本、切片器版本和固定 embedding profile（provider/model/dimension/encoding_format）均未变化，且现有 revision 的状态与目标模式相容，才复用现有 revision；semantic 已开启时，`lexical_only`、`embedding_failed` 或 `embedding_pending` 不能直接复用，用户点击刷新必须允许重试。发生变化时，Parser 输出带行号的 segment，Chunker 按标题、段落、代码符号或固定窗口生成 chunk，Normalizer 生成 FTS terms。semantic 关闭或没有凭据属于用户选择的 lexical 模式，候选 FTS revision 完成后直接切换为 active；semantic 已开启且请求实际失败时，候选 revision 保留为非 active 的 `embedding_failed`，已有 active revision 继续提供检索，只有首次索引且没有旧 active 才切换完整的 `lexical_only` revision。embedding 成功时所有批次向量校验通过后才一次性切换 `semantic_ready` active，状态必须明确显示。

Turn 执行时，AgentRuntime 只向模型公开 `search_knowledge` 和 `read_knowledge_citation`。模型先传自然语言 query，Retriever 在宿主侧根据线程绑定工作区和已启用 Collection 做过滤；先取 FTS5/BM25 候选，再按需调用一次 BGE-M3 对 query 编码，使用本地余弦相似度取得语义候选，最后以 RRF 融合、来源去重和预算裁剪。没有凭据、语义开关关闭、API 超时或向量缺失时，工具返回 `lexical_only` 元数据并继续提供 FTS 结果。每个结果生成绑定 threadId、turnId、revisionId 的 opaque citationId；模型需要上下文时只能读取已经返回的 citation，不能提交任意文件路径。

## **2.7 兼容分析**

| **类别** | **分析** |
|----------|-----------|
| 是否灰度? | 是。知识库总开关、Collection enabled 和 semantic enabled 均默认关闭；开启后仍可单独关闭自动检索或回退 FTS-only。 |
| 功能对新旧版本是否影响? | 不修改既有会话 JSONL、Memory、search_repository 或文档附件协议；知识事件使用独立 schema，SQLite 启动时执行向前 Migration。新增向量表可空，旧 revision 继续按 FTS 检索。 |
| 没有 embedding API Key 是否可用? | 可用。FTS5/BM25 是明确的降级路径；没有 Key 或 semantic 关闭时按 lexical 模式更新 active revision；已开启 semantic 但外部请求失败时保留旧 active（首次索引才切换 `lexical_only`），普通对话不受阻塞，结果标记 `lexical_only`。 |
| BGE-M3 是否必须固定? | 是。第一期固定 `provider=siliconflow`、官方 endpoint、`model=BAAI/bge-m3`、`encoding_format=float`；维度以首次成功响应为准。用户示例的 `Qwen/Qwen3-VL-Embedding-8B` 不在本期能力矩阵内，未来接入必须新建 profile 和全量重嵌入，禁止混用向量。 |
| 对代码仓库搜索是否替换? | 不替换。search_repository 继续做即时文件定位；知识库只搜索用户显式加入且成功索引的来源。 |
| 对现有文件是否复制? | 不复制工作区文件；只存相对路径、chunk 文本和可删除的向量 BLOB。工作区外文件导入、Blob 管理和云端资料均为二期。 |
| 对上下文预算是否影响? | 检索结果使用独立 knowledge budget，默认不超过工作上下文的 8% 且最多 6 个 chunk；向量查询只增加一次 embedding 请求，不把向量本身送入聊天模型。 |

| **事件** | **事件描述** | **触发频率** | **上级事件** | **风险识别** | **性能设计** |
|----------|----------------|----------------|----------------|----------------|----------------|

总结：风险主要集中在工作区边界、scope 过滤、索引代际一致性、第三方 embedding 可用性/数据外发、模型维度一致性和 citation 可验证性。TOP 风险是路径逃逸、禁用或跨项目来源被召回、未经确认向硅基流动发送正文、API Key 泄露，以及取消任务后半成品 revision 被切换；这些风险会直接影响数据隔离、隐私和回答可信度。

控制策略覆盖事前、事中和事后：事前使用规范化路径、精确文件选择、扩展名/大小校验、来源启用确认、语义检索 opt-in、HTTPS endpoint 白名单和唯一约束；事中使用有界任务、批量/退避、状态事件、active revision 门闩、脱敏日志、向量维度校验和 citation 校验；事后保留旧 revision、允许 embedding 失败降级为 FTS-only、支持任务取消/重试、来源删除审计、凭据删除和索引重建。

上线前专项复核必须确认：没有 API Key、API 限流或网络失败时 FTS-only 仍可用；语义开关关闭后不再产生 embedding 请求；禁用、删除或换工作区后不会向 SiliconFlow 或聊天 Provider 发送旧 chunk；请求使用正确的 `model`/`input`/`encoding_format`，日志不包含 API Key、完整知识正文或完整 query；每条可见 citation 均能定位到当前 revision 的正确文件和行区间。

# **3、 系统详细设计**

## **3.1 主要功能说明**

本期主要功能按以下编号实施：

1. K-01 知识库开关和 Collection 管理：用户可以启用/停用知识库并创建、编辑、删除集合。
2. K-02 工作区来源管理：用户选择当前工作区内的精确文本文件，后端保存来源元数据和文件指纹。
3. K-03 结构化切片和增量索引：解析文件、按结构切片、生成 FTS terms，并按内容/解析器/模型版本复用 revision。
4. K-04 SiliconFlow BGE-M3 embedding：按最多 32 条一批调用固定官方 `/v1/embeddings`，使用 `BAAI/bge-m3` 和 `encoding_format=float`，校验响应后保存本地向量；没有凭据或请求失败时按 active 保留策略降级。
5. K-05 混合检索：按线程工作区和已启用集合过滤，融合 BM25 与 cosine/RRF 结果，返回有界结果和 citation。
6. K-06 citation 读取：模型或用户只能读取本次检索签发的 citation，并可请求有限相邻上下文。
7. K-07 索引状态、取消和恢复：显示解析/embedding 阶段、错误和更新时间；取消或重启后不得留下假成功。
8. K-08 embedding 配置和凭据：展示固定 SiliconFlow endpoint/model profile，配置批量、超时和语义开关，API Key 只写操作系统凭据并可测试/删除。

## **3.2 次要功能说明**

本期包含的低成本约束：

- 只支持当前工作区内、用户明确选择的普通文本文件；不新增工作区外文件复制链路。
- 使用硅基流动托管的 `BAAI/bge-m3`，不下载或运行本地 embedding 模型；endpoint、model 和编码格式固定，不开放任意第三方地址；同时保留 SQLite FTS5/BM25 作为无 Key、限流或网络失败时的降级路径。
- 不引入 PostgreSQL/pgvector、Redis、Elasticsearch、HNSW 或远程向量数据库；向量只存本地 SQLite BLOB，由 Rust 做有界 cosine 扫描。
- 不做自动文件监听；索引只由添加来源或用户点击刷新触发，应用启动不自动扫描工作区。
- SiliconFlow 请求批量最多 32 项，默认 8～16 项；BGE-M3 单项输入不超过官方 8192 token 限制，默认 chunk 上限远低于该值；不使用 `truncate` 自动丢弃内容。
- 不把知识正文写入 system prompt；检索上下文作为非权威数据，必须带来源定位。
- 不允许模型创建/删除 Collection、添加来源、刷新索引、修改 embedding 配置或传入绝对路径。

二期或待确认内容：

- 待确认：是否需要支持 PDF、DOCX、Excel 的结构化页/Sheet locator；可以复用现有解析器，但会扩大测试和存储边界。
- 待确认：是否需要工作区外文件导入；若需要，应先设计受管 Blob 和删除/备份策略。
- 二期：本地 embedding 模型、第二个远程 embedding 服务、其他模型（包括 `Qwen/Qwen3-VL-Embedding-8B`）、专用向量索引、混合检索权重学习和 reranker。
- 二期：PostgreSQL/pgvector 服务端适配、多用户权限、远程同步和知识库共享。
- 二期：文件监听、定时增量索引、批量导入和索引质量评测面板。

| 性能设计 | 列表和新增响应不被全文解析阻塞 | 先写 source 元数据，索引放入有界后台任务 | 任务过多时需显示排队而非无限创建 |

| 隐私设计 | 不记录完整正文和敏感路径 | 保存相对路径、hash 和有界展示名；日志只记 ID | 文件名本身可能含敏感信息，日志需脱敏 |
| 不中断设计 | 索引失败不影响已有知识 | 新 revision 成功后才切换 active；失败保留旧版 | 用户必须看到旧版仍在使用 |
| 人因差错设计 | 删除和停用可恢复确认 | 删除前二次确认；停用只改 enabled | 误删事件仍会保留，恢复操作待确认 |
| 过载设计 | 限制来源数量和单文件大小 | 每集合来源数、单文件字节数、总 chunk 数设硬上限 | 超限需返回可读错误码 |
| 预防设计 | 避免重复来源 | 规范化 workspaceId + relativePath 唯一约束 | 工作区重命名会形成新来源，需明确迁移 |
| 冗余设计 | 元数据可重建 | JSONL 事实事件 + SQLite 投影；文件本体仍由工作区管理 | 工作区文件被外部删除时只能标记失效 |
| 配置化设计 | 可调整限制但不扩大安全边界 | 结果数、队列容量、语义开关和预算写 settings；endpoint、model 和 encoding profile 只读且由后端固定 | 用户配置错误必须关闭失败；未来切换 model 必须新建 profile 并重建 |

#### 设计细节

### **3.3.4 功能点 2（结构化切片、SQLite FTS5 与 BGE-M3 向量索引）**

#### 特性设计

| **特性** | **要求** | **实现方案** | **隐患说明** |
|----------|----------|----------|----------|
| 性能设计 | 小文件快速索引，重复刷新低成本 | SHA-256 + parser/chunker + embedding profile 命中时复用 revision；FTS 和向量批量事务写入 | 首次大批量仍会占用 CPU/网络，需显示阶段进度 |
| 安全设计 | 解析和外发均受边界控制 | 只接收已校验的工作区相对路径；不执行宏/脚本；只向固定 HTTPS endpoint 发送有界 chunk | endpoint 或错误处理新增分支需安全评审 |
| 隐私设计 | 用户明确知道正文会外发 | semantic 开关默认关闭；首次开启显示 SiliconFlow 数据外发提示；日志只保存 hash/计数/status/traceId | SQLite 向量和已发送正文仍属于用户敏感数据，需纳入删除/备份说明 |
| 不中断设计 | embedding 失败不阻塞知识库 | 新 revision 写入临时事务；已有 active 时保留旧版，首次索引才提交 lexical_only；成功后一次切换 | partial 向量不能伪装为完整语义索引 |
| 人因差错设计 | 用户可判断索引是否完整 | 显示状态、更新时间、文件大小、chunk 数和错误 | 截断内容必须明确标识 |
| 过载设计 | 解析、请求和向量扫描有界 | 单文件、单任务、总 chunk、请求批次、向量扫描和结果预览均有硬上限；请求数组最多 32，默认 8～16 | 达到上限不能静默丢尾部或无界读取向量 |
| 预防设计 | 结构边界和模型版本稳定 | Markdown 按标题/段落；代码按函数/类或行窗口；chunk 保存 locator；revision 绑定固定 provider/model/dimension/encoding profile | 无语法树或模型变更时要保证行号和重建边界可回溯 |
| 冗余设计 | FTS 可独立工作并可重建向量 | knowledge_chunks 保存原文和 terms；FTS 与 embedding 表均为派生索引；向量缺失时回退 FTS | FTS 或向量损坏时查询降级但不能读取越权来源 |
| 配置化设计 | 参数可调但默认保守 | target 600～1,000 token、max 1,500 token、overlap 10%～15%；batch/timeout 可设但受编译期上限限制，model/endpoint/encoding profile 固定 | 调参不得改变 locator、权限或 BGE-M3 不支持的 dimensions 语义 |

#### 设计细节

现状：现有 document parser 输出单一 DocumentContent，现有 search_repository 按行扫描且不持久化索引。目标：把解析结果转换为带 locator 的 segment，生成可重建 FTS5 chunk，并在用户 opt-in 后调用 SiliconFlow BGE-M3 生成向量。影响范围：新增 ParsedSegment/KnowledgeChunk/ChunkEmbedding 协议、SQLite Migration、EmbeddingClient 和后台 Indexer；既有附件提取保持原行为，不打包本地 embedding 模型。

切片规则按优先级执行：

1. Markdown/文本：先按标题和空行段落切分；单段超过最大值时按自然换行切分，并保留上一级标题作为 prefix。
2. 代码：优先识别函数、类、方法和 Rust/TS/C# 常见块；无法识别时按行窗口切分。每个 chunk 记录 startLine/endLine，不把不同文件合并。
3. JSON/YAML/XML：按顶层对象、数组项或缩进块切分；无法安全解析时按行窗口处理，不执行内容。
4. 路径、标题、符号名和表头加入 terms；内容本身保留原始 UTF-8 文本。
5. 目标 600～1,000 个估算 token，最大 1,500；相邻 chunk 只在同一结构块内重叠 10%～15%，跨标题或函数不强行重叠。该上限低于 SiliconFlow 文档中 BGE-M3 的单项 8192 token 上限，不使用 `truncate` 静默丢内容。

FTS 规范化规则：

- 拉丁字符和数字统一小写；保留原始文本用于展示。
- camelCase、PascalCase、snake_case、kebab-case、点号路径拆成独立词，并保留完整标识符。
- 连续中文字符生成二字词，限制每段最多 4,096 个词项；短文本保留原词。
- 查询同样经过规范化；短语优先，多个词默认 OR，并用命中词数、短语命中和 BM25 排序。
- 如果 FTS5 对某类 CJK 查询返回空结果，可以执行一次有界 LIKE 兜底，最多扫描 200 个候选 chunk；兜底仍受 scope 和 revision 过滤。

Embedding 输入和请求约定：

- 每个 chunk 的 embedding 文本由“相对路径（可选）+ 标题层级 + chunk 正文”组成，不包含绝对路径、API Key、运行时环境变量或未选中的文件；原文引用仍以 `knowledge_chunks.text` 为准。
- 使用 `POST https://api.siliconflow.cn/v1/embeddings`，Header 为 `Authorization: Bearer <账户 API Key>` 和 `Content-Type: application/json`；请求体显式发送 `model`、`input` 和 `encoding_format: "float"`。
- `input` 使用文本模型的字符串或字符串数组形式；批量最多 32 项，k-Coder 默认 16 项，空字符串拒绝。本期不发送 VL 模型所支持的图片 URL/base64 或混合对象。BGE-M3 和 `Pro/BAAI/bge-m3` 的官方单项上限为 8192 tokens。
- BGE-M3 不发送 `dimensions`，因为官方文档说明该字段仅支持 Qwen/Qwen3 系列；向量维度以响应数组长度为准（BGE-M3 常见为 1024），写入前必须与固定 model profile 一致。
- 响应要求 `object="list"`、`model` 与请求模型一致，`data[].object="embedding"`，`index` 覆盖 `0..n-1` 且无重复；`embedding` 每个元素必须是 finite number。`usage.prompt_tokens/completion_tokens/total_tokens` 只用于指标，不写入正文日志。
- 响应头中的 `x-siliconcloud-trace-id` 只作为脱敏诊断关联 ID 保存；不保存响应原文。官方错误状态 400/401/403/404/429/503/504 分别映射为参数、鉴权、权限、模型不存在、限流、过载和网关超时诊断。

Embedding 索引流程：

1. 本地完成路径校验、读取、SHA-256、解析、切片和 FTS terms 生成。
2. 若 semantic 关闭或没有凭据，直接提交 `lexical_only` revision（首次索引可成为 active），不产生外部请求；已有 active revision 不因配置关闭而删除。
3. 若 semantic 开启，按 8～16 个 chunk 组成数组请求；每批最多 32 项，超时/取消可中止请求，成功后立即校验 index、维度、数值范围并写入临时向量表。
4. 所有批次成功时将 revision 标为 `semantic_ready`；任一批次失败时丢弃临时向量，候选 revision 标为 `embedding_failed` 并保留为非 active；已有 active revision 继续服务，首次索引才允许提交无向量的 `lexical_only` revision。
5. parser/chunker 版本变化或未来切换模型 profile 时生成新的 revision；旧向量只能与其 provider/model/dimension/encoding_format 完全匹配时参与检索。对失败状态的相同 hash，用户再次点击刷新必须重新请求 embedding。

**revision 状态约定：** `lexical_only` 表示 FTS 已完整且没有可用向量（semantic 关闭、没有 Key，或首次 embedding 失败）；`embedding_pending` 表示任务中断、等待再次执行；`semantic_ready` 表示所有 chunk 都通过向量校验；`embedding_failed` 表示本次候选 revision 的外部请求失败，只能作为非 active 诊断记录。用户主动选择 lexical 模式时允许用 `lexical_only` 更新 active；被动 embedding 失败不得替换已有 active revision；任何状态都不得用零向量补齐。

### **3.3.5 功能点 3（BM25 + BGE-M3 混合检索与 citation）**

#### 特性设计

| **特性** | **要求** | **实现方案** | **隐患说明** |
|----------|----------|----------|----------|
| 性能设计 | 查询在本地快速完成 | FTS top 50 + 向量 top 50；向量按 256 条批次读取，工作区最多扫描 50,000 个 active chunk | 超过扫描上限必须标记 semantic_skipped，不得无界占用 CPU/内存 |
| 安全设计 | 检索不得越过线程工作区 | 从宿主得到 thread workspace、Collection enabled 和 model profile；模型参数只作为 query/limit | 禁止模型提交 collection scope、model、绝对路径或 endpoint |
| 隐私设计 | 外部 query/正文传输可审计 | semantic 开启时只发送当前 query 或已选 chunk；事件只写 queryHash、model、count、latency、status 和 traceId | 调试日志不得打印 query、chunk、Bearer 或响应原文 |
| 不中断设计 | embedding 失败不终止普通 Turn | FTS 和有界 LIKE 继续返回结果；工具 metadata 标记 lexical_only/semantic_unavailable；权限错误单独失败 | 不能把 FTS-only 结果宣称为语义命中 |
| 人因差错设计 | 命中结果可复核 | 返回来源名、相对路径、行区间、citationId、更新时间、retrievalMode 和模型状态 | 过期 revision 或降级状态必须明确显示 |
| 过载设计 | 上下文和外部请求有界 | 最多 6 个 chunk、单 chunk 6,000 字符、总知识预算 8%；每次搜索最多 1 次 query embedding | 长 chunk 需首尾裁剪并标 truncated；查询缓存有大小/TTL 上限 |
| 预防设计 | 防止相同来源霸占结果 | 同一 source 最多 3 条，重叠 chunk 去重并可合并相邻窗口；RRF 平分时按 BM25/ordinal 稳定排序 | 合并后 locator 必须覆盖完整范围 |
| 冗余设计 | 词法和语义互为降级 | FTS 无命中可执行一次有界 LIKE；向量缺失、Key 不存在或 API 错误时回退 FTS | 不得把零向量或旧模型向量当作有效候选 |
| 配置化设计 | 结果数和预算可调 | settings 允许收紧 limit、scan cap、timeout 和 semantic 开关；model/endpoint/encoding profile 为固定能力事实 | 非法配置关闭失败，BGE-M3 不发送 dimensions |

#### 设计细节

现状：现有 search_repository 返回路径、行号和预览，但没有集合、revision、citation 或 Turn 绑定。目标：把“搜索已索引知识”作为独立只读工具，融合 FTS5/BM25 与 SiliconFlow BGE-M3 cosine 结果，并让每个结果都能回到同一份 active revision。影响范围：新增 Retriever、EmbeddingClient、VectorStore、CitationStore、ToolRegistry 注册和 AgentRuntime 工具结果历史；不改变原有 search_repository。

检索流程：

1. 校验 query 长度 1～256 个字符，拒绝空白和控制字符。
2. 从 ToolContext 取得 threadId、turnId、workspaceRoot；由宿主计算可见 workspaceId 和 enabled Collection，不接受模型覆盖。
3. 将 query 规范化为词项和短语，使用 FTS5 tokenizer/转义规则构造并绑定 `MATCH` 参数，禁止把原始 query 当作 SQL/FTS 表达式执行；取最多 50 个 lexical 候选，必要时执行一次最多 200 个候选的 CJK `LIKE` 兜底。
4. 过滤 source.deleted、collection.enabled=false、revision.active=false、workspaceId 不同、固定 model profile 不匹配和 chunk 过期状态。
5. 若 semantic enabled 且有 SiliconFlow 凭据，使用 `input` 字符串调用固定 `/v1/embeddings`，显式发送 `model="BAAI/bge-m3"` 和 `encoding_format="float"`，不发送 `dimensions`；响应通过 index、model、维度和 finite 校验后，在最多 50,000 个 active chunk 上计算归一化 dot product，取 top 50。
6. 使用 Reciprocal Rank Fusion（`1 / (60 + rank)`）融合 lexical/vector 两路；同一 source 最多 3 条，重叠 chunk 去重，相同分数按 lexical rank、path、ordinal 稳定排序。
7. 没有 Key、semantic 关闭、API 返回 401/403/404/429/503/504、超时、维度不符或超过扫描上限时，保留 lexical/LIKE 结果并设置 `retrievalMode=lexical_only` 与脱敏 fallback code；不得重试无效参数或把失败向量填零。
8. 合并高度重叠相邻 chunk，裁剪到最多 6 条和 8% knowledge budget；为每条结果生成随机 opaque citationId，并把 citation 与 thread、turn、revision、chunkId 和过期时间写入有界内存/SQLite 快照。
9. ToolResult 输出结构化 JSON；metadata 含 queryHash、resultCount、retrievalMode、embeddingModel、semanticCandidateCount、fallbackCode、retrievalRevision 和 truncated，不含完整 query、向量或正文摘要。

query embedding 只在 semantic enabled 且当前 Turn 确实执行语义搜索时产生；可使用进程内最多 128 项、10 分钟 TTL 的 LRU 缓存，键为 `sha256(profile + query)`，不持久化 query 或向量。缓存命中不重复请求 SiliconFlow，能力 profile 变更或删除凭据时立即清空。

read_knowledge_citation 只接受本次 Turn 已签发的 citationId，以及可选 before/after 取值 0～1。服务端从 citation 表查 chunk，不把 path 交给 read_file；如果工作区文件已变化，仍可读取已索引的 chunk 文本，但标识其 revision 已非当前 active，不能 silently 当作最新事实。

### **3.3.6 功能点 4（索引状态、取消恢复与设置页，含 embedding 配置）**

#### 特性设计

| **特性** | **要求** | **实现方案** | **隐患说明** |
|----------|----------|----------|----------|
| 性能设计 | 设置页不阻塞对话 | 任务进度通过事件或轮询快照更新，正文懒加载；embedding 批次显示 processed/total | 高速进度事件和网络重试需合并 |
| 安全设计 | 只有用户可控制索引和外发 | 管理命令不注册为模型工具；删除/启用 semantic 要求确认；endpoint 只允许 HTTPS | UI 控件不替代后端检查 |
| 隐私设计 | 状态页不展示正文或 Key | 只展示文件名、大小、hash 前缀、chunk/向量数、模型名和错误摘要；Key 仅显示 configured | 文件名、模型和外发状态仍需清晰披露 |
| 不中断设计 | 重启后状态可恢复 | running 任务启动恢复为 queued/failed；active revision 保持 | 恢复时需复核文件指纹 |
| 人因差错设计 | 操作结果明确 | 显示“未索引/索引中/已完成/仅词法/语义失败待重试/失败/已过期”，标注固定 endpoint/model 和最后错误 | 错误文案需对应结构化 code，不能把免费限流说成永久故障 |
| 过载设计 | 防止重复点击和外部超额 | source 级幂等键、按钮忙碌状态、单并发和批量上限；查询缓存有 TTL | 竞态请求仍需后端合并，不能无限重试 |
| 预防设计 | 旧任务不能覆盖新任务 | revision hash 和 job generation 比较后才允许切换 | 过期任务只能标 cancelled |
| 冗余设计 | 索引可以重建和降级 | 提供来源级重建；FTS 不是唯一事实，向量缺失时 lexical_only；embedding 失败保留旧 active | 重建期间继续读旧 active revision，不能删除唯一可用索引 |
| 配置化设计 | 默认低成本、可控外发 | 默认 semantic=false；batch/timeout/scan cap 可设但有编译期上限；endpoint/model/encoding profile 固定；API Key 独立凭据 | 不提供“无限制”选项，不允许把 Key 写入普通设置 |

#### 设计细节

现状：现有设置页已有 Memory 管理和多种运行时设置，但没有知识来源、索引作业或 embedding 配置投影。目标：新增独立“知识库”设置入口，不把它命名为“记忆”；用户可以看到集合、来源、状态、刷新和删除，并能明确配置/测试 SiliconFlow embedding。影响范围：SettingsDialog、前端 runtime API/types、Tauri commands、CredentialStore 和后端任务事件；不改变 MemoryPage 的数据与命令。

页面最低交互：

- 总开关默认关闭；semantic 开关单独默认关闭。开启 semantic 前说明“选定来源和检索 query 会发送到硅基流动”，并给出官方 API 文档链接。
- Embedding 配置显示固定 provider=SiliconFlow、endpoint、model=`BAAI/bge-m3`、BGE-M3 8192 token 单项上限、batch（默认 16、最大 32）、请求超时、向量扫描上限和 `encoding_format=float`；endpoint/model/profile 只读，BGE-M3 不展示/提交 `dimensions`。
- API Key 输入框只提交一次性写入命令，保存后仅显示“已配置”；提供测试连接和删除凭据，测试只发送固定短文本，不发送工作区正文。
- Collection 行显示名称、scope、来源数量、启用开关和删除按钮。
- Source 行显示相对路径、文件大小、最后索引时间、状态、chunk 数、向量数、model profile 和刷新/取消按钮。
- 失败状态显示结构化错误码和首条安全诊断；不显示完整堆栈、正文或绝对路径。
- 删除 Collection 先确认，再追加删除事实；UI 从后端刷新，不能仅从 Zustand 移除。
- 对话时间线只显示紧凑“查阅知识库”事件；展开可见来源和 locator，引用点击使用 citation 命令。

### **3.3.7 功能点 5（AgentRuntime 接入和上下文预算）**

#### 特性设计

| **特性** | **要求** | **实现方案** | **隐患说明** |
|----------|----------|----------|----------|
| 性能设计 | 不增加每一轮无谓模型调用 | 只在设置开启且 query 有效时按需调用工具；同一 Turn 快照和 query embedding 复用 | 自动预检索策略待确认；外部 API 延迟需有界 |
| 安全设计 | 知识正文不是指令，外部请求不可被模型控制 | 以非权威 context/tool result 注入，不改变工具集合和 Policy；endpoint/model 从固定能力 profile 读取 | 恶意文档可能诱导模型，需提示不可信；模型不能改 endpoint |
| 隐私设计 | 压缩和历史不泄露正文/Key | ContextBudget 单独计算 knowledge；事件只存摘要元数据；Provider 历史不保存 Bearer 或向量 | Provider 历史仍可能包含工具结果，需有界并提示外发状态 |
| 不中断设计 | 无索引或 embedding 不可用时仍可回答 | search_knowledge 返回 no_match/disabled/lexical_only，AgentRuntime 继续 | 模型不能把无命中或 lexical-only 说成已完成语义查证 |
| 人因差错设计 | 用户知道引用来自哪里 | 时间线展示“查阅知识库”和来源链接 | 引用失效需显示旧 revision |
| 过载设计 | 控制 Provider 输入和外部调用 | knowledge budget 默认工作窗口 8%，最多 6 chunks；每次搜索最多 1 次 query embedding，批次和向量扫描有上限 | 与历史/工具预算和 SiliconFlow TPM 限制必须再次估算 |
| 预防设计 | 防止 Compaction 递归 | 快照/工具结果不是真实 UserMessage，不写入摘要请求身份 | 压缩后需保留 citation 元数据而非正文 |
| 冗余设计 | 工具和预检索可并存且可降级 | 预检索关闭时模型仍可显式调用 search_knowledge；向量失败回到 FTS/LIKE | 不能重复追加相同 chunk 或重复请求同一 query |
| 配置化设计 | 可逐步启用 | global enabled、collection enabled、semantic enabled、autoSearch 分层开关；batch/timeout 可调，model/endpoint/profile 固定 | 默认值必须关闭，固定 profile 不可被请求参数覆盖 |

#### 设计细节

现状：AgentRuntime 已有独立上下文预算、ToolRegistry 和工具结果历史。目标：只新增两个只读工具和一个有界知识上下文类型，不把知识内容拼入 memory/system 指令；由宿主在需要时使用固定 SiliconFlow BGE-M3 profile 生成 query embedding。影响范围：tool registry、provider history/context budget、EmbeddingClient、公共事件和前端时间线；保留既有 ToolResult 配对、取消和 Compaction 语义。

第一期默认不做“每个用户问题自动调用一次知识搜索”的隐式模型前置请求，以避免额外复杂度、网络延迟和不可预期外发。模型在系统工具说明中得知 search_knowledge 的用途，由模型在需要项目文档事实时显式调用；调用后由宿主决定是否生成 query embedding，模型不能直接请求 endpoint 或 model。待评测证明需要自动召回后，再增加宿主预检索开关；该开关仍需一次查询、一次 query embedding、一次快照和独立预算。

知识工具结果使用结构化格式：

~~~json
{
  "success": true,
  "results": [
    {
      "citationId": "kc-opaque-id",
      "title": "架构设计",
      "path": "docs/架构.md",
      "locator": {"type": "fileLines", "startLine": 193, "endLine": 210},
      "preview": "JSONL schema 9 是对话和 Turn 事件的持久化事实来源……",
      "revision": "rev-opaque",
      "score": 0.842,
      "lexicalRank": 2,
      "semanticRank": 1
    }
  ],
  "metadata": {
    "resultCount": 1,
    "queryHash": "sha256:...",
    "retrievalMode": "hybrid",
    "embeddingModel": "BAAI/bge-m3",
~~~

Provider 历史只保存有界 ToolResult；ContextBudget 估算知识正文并在超过上限时按 RRF 分数和来源多样性裁剪。向量本身、Authorization Header、API Key 和 SiliconFlow 响应原文永不进入 Provider 历史。Compaction 只保留“检索过哪些 revision、citation 数量、query hash、retrievalMode 和 model profile”等元数据，不把完整知识正文当作真实用户消息，也不把 citationId 当作文件权限。

#### 数据库设计

不新增 AgentRuntime 专属表；知识快照和 citation 使用 3.3.5 表，线程事件仍由现有 ThreadRepository 管理。公共协议新增 KnowledgeRetrievalSnapshot、KnowledgeCitation 和 KnowledgeToolResult 的版本字段，建议初始版本为 1；协议只传 preview、score、locator 和 retrievalMode，不传向量或 API 凭据。

# **4、 事件分析**

| **事件名称** | **每日触发量** | **作用** |
|----------|----------|----------|
| 知识来源添加 | 预估每用户 0～50 次/日 | 创建 source 元数据并触发一次增量索引 |
| 来源刷新 | 预估每用户 0～20 次/日 | 比较文件 hash，未变化时直接复用 revision |
| FTS/Embedding 索引任务 | 与添加/刷新相同，批量任务按文件数拆分 | 生成 chunk、terms、BGE-M3 向量和 FTS/向量投影 |
| SiliconFlow embedding 请求 | 每个索引批次 1 次；默认每批 16 条，最多 32 条 | 生成 chunk 向量；受用户 semantic 开关、API 额度和网络状态约束 |
| 知识搜索 | 预估每个 Turn 0～8 次 | 为模型返回有限 lexical/vector 候选和 citation；每次最多 1 个 query embedding 请求 |
| citation 读取 | 预估每个 Turn 0～8 次 | 为模型提供已授权的相邻上下文 |

以上为第一期容量估算，不是计费承诺；上线后通过脱敏指标校准。SiliconFlow 的免费/低成本额度、TPM 限制和模型可用性以账户与服务方实时策略为准，不能在产品中承诺永久免费或不限量。`usage.prompt_tokens/completion_tokens/total_tokens` 只用于本地脱敏指标，不用于向用户虚构费用。

## **6.3 隐私保护**

| **检查项** | **检查结果** | **措施** |
|----------|----------|----------|
| 是否存在收集个人隐私的功能？ | 可能存在，取决于用户选择的文件 | 默认不扫描工作区；只索引用户明确选择的精确文件 |

| 是否使用第三方模型处理正文？ | 本期是，可选 opt-in | SiliconFlow `BAAI/bge-m3` 仅在 semantic 开启且请求确实发起后处理用户选定 chunk 和当前 query；关闭 semantic、无 Key 或请求失败后不再继续外发，并回退 FTS-only |

|----------|----------|
| 200 | 请求成功 |
| 400 | 参数错误、空 query、非法名称或配置超限 |
| 401 | 当前会话或宿主凭据无效；SiliconFlow 401 映射为 embedding 凭据失败 |
| 403 | Collection 未启用、线程无工作区、来源不在当前 scope 或 SiliconFlow 拒绝访问 |
| 404 | Collection、source、job 或 citation 不存在 |
| 409 | 同一来源已有活动任务、revision 发生变化或删除冲突 |
| 413 | 文件、提取正文、chunk 或结果超过有界上限 |
| 422 | 文件类型不支持、编码无效或解析失败 |
| 499 | 用户取消索引或查询 |
| 500 | SQLite、事件日志或内部任务错误 |
| 502 | SiliconFlow 返回 503/504、网络网关或 TLS 失败；可回退 FTS-only |
| 429 | SiliconFlow 返回 429 限流；最多退避重试 2 次，之后回退 FTS-only |

| 错误码 | 错误信息 | 说明 |
|----------|----------|----------|

| KC_NO_MATCH | no active knowledge match | 正常无命中，不等同于系统故障 |

#### **7.2.2.3 接口封装**

- Tauri 层：commands/knowledge.rs 只负责 serde 反序列化、参数长度/枚举校验、AppState 调用和 CommandError 映射；embedding Key 不经普通日志或响应返回。
- 领域层：KnowledgeService 暴露 collection、source、index、embedding-config、retrieval、citation 方法；每个方法接收宿主生成的 WorkspaceContext，不接收模型可控的授权字段。
- 存储层：KnowledgeRepository 负责 SQLite Migration、事务、JSONL 事实追加、投影重建和有界分页；FTS5、chunk 和 vector 表均可删除重建，vector 表按 profile 隔离。
- Embedding 层：EmbeddingClient 负责 HTTPS、Bearer 注入、批量/超时/退避、响应 index/维度/finite 校验、traceId 提取和错误脱敏；VectorStore 只接受已归一化 f32。
- 工具层：KnowledgeSearchTool 和 KnowledgeCitationTool 实现现有 ToolHandler，沿用 Schema 校验、PolicyEngine、CancellationToken、ToolResult 和审计；模型不能直接调用 EmbeddingClient。
- Agent 层：AgentRuntime 只把工具定义和有界结果加入 Provider 历史；KnowledgeSnapshot 不成为真实用户消息，不改变 Compaction 的请求身份。
- 错误层：内部错误转换为稳定 KC_* code 和脱敏 message；不以 UI 文案、SQLite 错误全文或模型返回字段决定权限。
- 版本层：Knowledge 协议和事件使用独立 schemaVersion=1；第一期 embedding profile 以 provider/固定 endpoint/model/dimension/encodingFormat 组成稳定指纹，未来增加字段必须向前兼容，未知版本关闭失败。

## **7.3 定时服务**

| 执行顺序 | 定时任务 | 执行时间 | 定时任务入参 |
|----------|----------|----------|----------|
| 1 | 本期不设置自动定时索引或后台批量 embedding | 不涉及 | 不涉及 |
| 2 | 用户点击添加来源或刷新时创建一次性解析/FTS/embedding 任务 | 按用户操作 | sourceId、当前文件指纹、embedding profile |
| 3 | 二期可评估工作区变更检查 | 待确认 | workspaceId、扫描间隔、单次预算 |

本期不启动文件监听器、不在后台周期性扫描工作区，也不因应用启动自动上传或生成 embedding。只有用户触发添加/刷新，且 semantic 开启并配置 Key 时才调用 SiliconFlow；定时索引若在后续版本启用，必须先补充调度开关、取消/退出语义、容量评估和 FMEA。
