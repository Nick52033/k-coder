# ADR 0004：有界多智能体运行时

- 状态：已接受
- 日期：2026-07-24

## 背景

并行仓库分析可以降低独立任务的等待时间，但直接为子智能体复制模型循环会产生两套权限、取消、持久化和工具语义。共享工作区并发写入还可能覆盖用户或其他智能体刚完成的修改。

## 决策

1. `multi_agent` 只负责委派生命周期。每个子智能体使用独立线程和普通 `AgentRuntime`，复用 Provider、工具注册表、策略、审批和事件契约。
2. 主智能体使用六个结构化工具创建、等待、发消息、恢复、列表和关闭子智能体。改变外部状态或产生新模型成本的操作按 `External` 风险审批。
3. 子智能体只能获得父工具注册表的显式子集和创建时固定的规范工作区。默认 Capability 是只读目录与文件。
4. 最大深度为一层，并发上限使用原子信号量强制为 4。Token 预算跨后续 Turn 累计；运行时长由取消感知的超时控制。
5. 子智能体令牌派生自父取消令牌。关闭子智能体或取消父 Turn 会传播到 Provider 请求和活动工具。
6. 写工具继续使用审阅时哈希、写入前复核和共享编辑锁。同一路径的并发修改最多一个成功，其余返回显式冲突。
7. 生命周期以完整有界快照追加到 `subagents.jsonl`。应用重启时仍处于活动状态的记录标记为失败。主智能体只接收结构化状态和最多 32 KiB 的摘要，不接收隐藏对话历史。
8. 活动界面位于主窗口右侧面板，展示运行、阻塞、失败、完成、预算、摘要和控制操作。

## 影响

收益：

- 并行委派不绕过已有安全边界，也不需要第二套智能体循环。
- 权限、预算、取消、冲突和恢复都有确定性宿主约束。
- 主上下文只接收有界结果，避免把全部子会话复制回父上下文。

成本与限制：

- 当前只允许一层委派，且不提供自动 worktree 隔离。
- 共享工作区适合并行读取或不同文件修改；同文件替代方案仍应使用独立 worktree。
- 重启后不会自动重放未完成模型请求，而是要求用户显式恢复。

## 未采用方案

### 每个智能体一套新循环

未采用，因为会复制 Provider、工具、审批、取消和持久化逻辑，并让安全修复容易只覆盖其中一套。

### 默认允许任意工具和递归委派

未采用，因为子智能体不能扩大父权限，递归委派也会使成本和取消范围难以预测。

### 依赖最后写入获胜

未采用，因为它会静默覆盖并行智能体或用户的修改。所有写入必须保留哈希冲突检测。
