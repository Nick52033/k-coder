# ADR 0037：工作上下文成本预算与结构化压缩

## 状态

已接受，2026-08-16。

## 背景

模型配置中的 `contextWindow` 同时被用作 Provider 能力声明和 Compaction 预算。长 Turn 在接近模型硬窗口时才压缩，导致工具历史、系统规则和工具 Schema 在多轮请求中反复计入输入；即使单次请求没有超出窗口，累计输入也可能迅速达到百万级。

已有的确定性 Compaction 可以避免上下文超限，但旧摘要主要保留用户约束和最近工具结果。普通的最新用户请求、测试失败原因和工具输出中的高信号事实可能在压缩后丢失，进而造成模型重复读取文件或重复执行验证。

## 决策

1. 模型的 `contextWindow` 继续表示 Provider 的硬上限，不因成本优化而伪造或扩大。默认 `128,000` 窗口使用独立的 `96,000` 工作上下文基准；工作基准可通过运行时 Builder 覆盖，但始终夹在硬上限以内。
2. Compaction 判断同时估算消息历史、运行时指令和 Provider 工具 Schema，并继续参考最近一次 Provider `total_tokens`。工作基准的 65% 作为高水位；压缩后的历史只保留工作历史预算的四分之一，并把摘要限制在同等规模，形成明显的低水位，避免刚压缩就再次触发。
3. `CompactionSummary` 升级为契约版本 3，向后兼容旧摘要，增加当前用户请求、高信号工具观察以及压缩前后本地估算 token。原始 JSONL 事实不删改，新增字段只用于 Provider 历史和本地诊断。
4. 高信号工具观察使用本地确定性规则提取错误、失败、测试、退出码、路径、修改和中英文等关键词所在行，并设置数量和字节上限；它不是额外的模型摘要请求，不产生新的 Provider token。
5. Provider-facing 工具 Schema 对扩展工具的顶层描述设置 2 KiB 上限；完整定义仍用于本地校验和分发。工具结果上限从 256 KiB 降至 128 KiB，超限时保留首尾并写入原始长度和省略长度元数据。
6. Runtime Metrics 持久化每次压缩的前后估算规模、压缩消息数和自动/手动来源，并在快照中汇总压缩次数和估算节省 token。指标不得记录用户正文、完整工具输出、API Key 或请求头。

## 后果

- 默认请求更早离开 128k 硬窗口边缘，长 Turn 的重复输入预计下降；实际收益以回放指标为准，不能把估算节省直接当作供应商账单折扣。
- 确定性摘要仍可能丢失未命中高信号规则的细节，因此保留最近用户请求、近期工具结果和完整持久化审计，并通过回放测试监测重复读取。
- 扩展工具的超长说明或结果不再无界占用每一轮 Provider 输入；工具名称、Schema 结构和本地授权契约不变。
- 旧 v1/v2 `CompactionSummary` 缺少新增字段时按默认空值恢复，旧会话无需重写。

## 验证

- 上下文单元测试覆盖硬/工作窗口归一化、指令和工具 Schema 估算、低水位压缩、v1/v2 摘要兼容和工具配对修复。
- 固定的 19 轮工具回放比较硬窗口与工作窗口的累计估算输入，并断言工作基准发生压缩且总估算更低。
- 工具 Schema 描述上限、工具结果首尾保留和指标聚合均有确定性测试。
- 继续执行既有 `pnpm build`、Rust 格式/检查/全量测试，以及 `pnpm tauri dev` 的桌面启动验证。
