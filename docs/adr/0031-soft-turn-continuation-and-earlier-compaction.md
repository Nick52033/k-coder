# ADR 0031：普通 Turn 分段续跑与提前压缩

## 状态

已接受，2026-08-09。本 ADR 修订 ADR 0013 中“普通 Turn 默认完全不设置宿主资源停顿”的决定，但不恢复固定生命周期调用上限，也不改变显式 Goal/子智能体预算、权限、取消和无进展检测边界。其 65% 阈值后来由 ADR 0037 明确为工作上下文基准的高水位，模型 `contextWindow` 继续作为硬上限。

## 背景

ADR 0013 允许持续取得结果的复杂 Turn 超过固定调用次数，解决了 24 次上限误杀真实任务的问题。但普通 Turn 没有 Goal 时也完全依赖用户主动停止：模型只要持续返回新的工具调用，就可以在看似“有进展”的情况下执行数十轮。逐轮 Provider 历史又会重复携带工具结果，使累计 Token 消耗远高于单次上下文窗口，例如 95 次调用可累计到数百万 tokens。

累计 Token 是每次 Provider 请求用量的总和，本身不等于单次上下文超限；真正需要控制的是未经用户确认的连续执行段，以及压缩前长期携带的高水位上下文。

## 决策

1. 仅普通、无活动 Goal 的根 Turn 默认启用分段软续跑门。每段额度为 30 次 Provider 请求、1,000,000 累计 tokens 或 10 分钟墙钟时间，任一达到即在当前工具批次完成后的安全边界暂停；内部 Provider 重试计入请求次数和已返回的 Usage。
2. 软额度不是 Turn 生命周期硬上限。运行时通过既有、可持久化的 UserInput Item 发出 `kind = turn_continuation` 请求，不新增平行的 `TurnPaused` 状态或第二套等待管理器。
3. 用户选择“继续执行”后重置本段三项计数；选择“压缩后继续”还会在下一次 Provider 请求前强制尝试 Context Compaction；两种续跑都可以重复确认，不限制整个 Turn 的最终调用总数。
4. 用户选择“停止执行”，或请求被跳过、超时、取消、返回未知动作时，以 `turn_cancelled` 结束。请求和解决事件继续遵循 ADR 0019 的 UserInput Item 持久化、发布和闭合顺序。应用重启时既有崩溃恢复会取消未完成交互和 Turn，不把已失效的进程内等待恢复为可操作状态。
5. 显式 Token 预算仍是硬失败边界并优先执行；Goal 时间预算和子智能体时长边界保持不变。活动 Goal 的根 Turn 和子智能体不叠加普通 Turn 软门，避免改变既有自治任务语义。
6. 自动 Compaction 阈值从模型窗口的 80% 提前到 65%，最近完整工具结果从 4 个减为 2 个。压缩上下文中超过 4 KiB 的工具输出不保留全文，改为包含原始字节数、行数、首段和尾段的确定性摘要；完整审计结果仍保留在 JSONL 事实事件中。
7. 软门只在安全轮次边界检查，因此当前进行中的 Provider 请求、内部重试序列或工具批次不会被额度本身切断，实际计数可小幅超过阈值。用户取消和显式硬预算仍可按各自边界立即生效。

## 后果

- 没有 Goal 的普通 Turn 最多连续执行一个分段额度就必须获得用户确认，95 轮无人值守续跑会在更早位置被拦截。
- 用户仍能明确选择继续完成大型任务，ADR 0013 的“无固定生命周期调用上限”目标继续成立。
- 提前压缩和工具输出摘要减少后续每轮重复输入，但不会把累计 Token 误当成当前上下文长度，也不会删除持久化审计事实。
- `UserInputRequest.kind` 成为公共类型化契约；旧记录缺少该字段时默认恢复为 `model_question`。

## 验证

- 达到一段调用额度后会持久化 `turn_continuation` 请求；选择继续后进入下一次 Provider 请求并获得新额度。
- 选择停止后 Turn 为 cancelled，且不会发出下一次 Provider 请求。
- 选择压缩后继续会在下一次 Provider 请求前产生自动 Compaction 事实（存在可压缩历史时）。
- 调用次数、累计 Token 和分段时长任一达到阈值都能触发软门；没有完成过 Provider 请求时不会仅因时钟触发初始弹窗。
- 旧 UserInput JSON 缺少 `kind` 时仍可反序列化为模型提问。
- 65% 用量触发压缩，只保留最近两个工具结果，超过 4 KiB 的结果进入有界摘要。
