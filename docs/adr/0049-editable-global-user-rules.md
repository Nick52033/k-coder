# ADR 0049：可编辑的全局用户规则

- 状态：已接受
- 日期：2026-08-31

## 背景

ADR 0003 已确定扩展指令按全局、项目根和项目规则分层编译，但此前设置页只能查看指令来源，用户若要增加长期规则，必须手工修改应用数据目录中的 `AGENTS.md` 或项目文件。参考 Cursor 的 User Rules 交互，需要在设置中直接新增、编辑和删除多条规则，同时不能把浏览器状态变成运行时事实，也不能削弱扩展的路径、大小、审计和关闭失败边界。

## 决策

1. 全局用户规则使用应用数据目录中的专用 `runtime-data/user-rules.json`，schema v1 保存有序规则数组。每条规则包含宿主生成的 UUID、名称、正文、创建时间和更新时间；前端不能指定时间或为新规则指定 ID。
2. 指令优先级固定为：全局 `AGENTS.md` 为 100，用户规则按数组顺序从 110 递增，项目 `AGENTS.md` 为 200，项目 `.k-coder/rules/*.md` 从 300 递增。后出现的指令在冲突时优先，因此项目约束仍可覆盖全局用户规则。
3. 用户规则继续由唯一 `extensions` 运行时编译，只进入现有项目会话的 Provider 请求，不增加工具、不改变 `PolicyEngine`，也不为显式无项目会话恢复项目扩展能力。
4. Tauri 只公开类型化的 `user_rules`、`save_user_rule` 和 `delete_user_rule` 命令。React 设置页不直接访问文件系统，不使用 `localStorage` 保存规则正文。
5. 配置最多 64 条规则、单条名称最多 80 个可见字符、单条正文最多 16 KiB、文件最多 256 KiB。读取和写入前必须解析作用域路径并拒绝链接逃逸；JSON 拒绝未知字段、非法或重复 ID、无效时间和空正文。
6. 写入使用同目录唯一临时文件并同步内容；Windows 替换旧文件时保留可恢复备份直到新文件就位。审计只记录规则 ID 和动作，不记录名称或正文。
7. 保存或删除后立即重建扩展注册表并记录审计。若其他扩展导致重建失败，规则文件仍保留已确认的用户修改，返回视图同时展示运行时错误，后续扩展准备继续关闭失败。
8. 设置页使用紧凑规则列表、页内新增/编辑表单和明确的删除确认；运行时来源与扩展审计作为次级折叠信息保留。

## 影响

收益：

- 用户可以在设置中维护多条长期规则，重启后继续生效。
- 用户规则、项目规则和 `AGENTS.md` 的覆盖关系确定且可测试。
- 规则正文不进入前端临时存储、扩展审计或结构化日志。
- 配置损坏、越界链接和超限输入不会静默降级。

成本与限制：

- 当前设置页只管理全局用户规则；项目 `.k-coder/rules` 仍由项目文件维护。
- 当前不提供拖拽排序、单条停用或规则条件匹配；数组顺序只由创建顺序和配置文件直接编辑决定。
- 显式无项目会话仍不加载扩展运行时，因此不会应用这些规则。

## 未采用方案

### 使用 `localStorage` 保存规则

未采用，因为前端状态不能成为 Provider 指令的持久化事实来源，也无法复用后端校验、审计和关闭失败语义。

### 直接覆盖全局 `AGENTS.md`

未采用，因为设置页无法安全区分用户创建的独立规则与已有手工指令，编辑或删除时容易覆盖其他内容。

### 每条规则保存为独立 Markdown 文件

未采用，因为标题、稳定 ID、顺序和原子多条更新需要额外索引，增加了文件与索引不一致的恢复状态；有界 JSON 文档更适合当前 CRUD 契约。
