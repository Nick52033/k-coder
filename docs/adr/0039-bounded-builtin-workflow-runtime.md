# ADR 0039：以内置受限工作流实现机器人

- 状态：已接受
- 日期：2026-08-16

## 背景

k-Coder 已有唯一 `AgentRuntime`、Goal/Plan 高级能力、Skill 扩展、线程 mailbox、工具策略和追加式事实存储。cn-codex 的内置机器人本质上也是主智能体上的角色与阶段覆盖，但其节点推进依赖模型输出特殊标记，角色 prompt 可能只存储而没有实际注入，Skill 引用和外部副作用也缺少统一的宿主校验。

直接复制一套机器人循环会违反现有架构边界，并让取消、预算、工具审批、工作区绑定、持久化和子智能体约束出现第二套实现。只做前端 prompt 模板则无法可靠恢复或审计节点状态。

## 决策

1. 机器人定义为主 `AgentRuntime` 上的版本化内置工作流，不创建新的 Agent 循环。首个版本提供全栈开发、质量保障和需求设计三个只读定义。
2. 工作流运行实例绑定项目线程，以追加式 `advanced/workflows.jsonl` 快照持久化。独立会话不能启动项目工作流。
3. 首条消息通过可选 `workflowId` 启动运行实例；后续 Turn 和 retry 从后端状态恢复，不依赖前端重复提交。
4. 后端在每个 Turn 的受控 system prompt 中真实注入角色、目标和当前节点。宿主安全、AgentMode、工具 Capability 和 Policy 的优先级始终高于工作流指令。
5. 节点推进只接受 `complete_workflow_node` 工具，要求精确当前节点、非空总结和有界证据。特殊文本标记、普通最终回复和模型传入的下一节点均不能改变状态。
6. 工作流不自动加载或启用 Skill、MCP、Hook 和子智能体，不携带授权字段，也不触发钉钉、禅道、Git push 等外部副作用。所有普通工具继续走既有授权和审计边界。
7. 首个版本不提供用户定义文件、可视化编排、条件分支或并行节点；设置页 Workflows 继续标记为后续能力。

## 影响

- 机器人可以跨 Turn 和应用重启恢复，并复用现有 Provider、Compaction、取消、审批和工具历史。
- 工作流状态与线程 JSONL 分开保存，和现有 Goal/Plan 高级存储一致；界面通过专用命令读取投影。
- 内置定义更新必须保持已有 workflow/node ID 稳定，删除或重命名需要显式迁移政策。
- 结构化证据只能证明模型提交了可审计依据，不能替代测试真实性；真实性仍由工具结果、变更事实和用户审查共同判断。

## 验收门槛

- Rust 测试覆盖定义完整性、状态迁移、跨实例恢复和所有关闭失败分支。
- 公共请求与前端类型新增字段保持可选，旧 mailbox 与旧调用可反序列化。
- 项目/独立会话边界、运行中切换限制和停止路径有回归测试。
- `pnpm build`、Rust 格式检查、`cargo check`、`cargo test` 和实际 Tauri 桌面验证通过。
