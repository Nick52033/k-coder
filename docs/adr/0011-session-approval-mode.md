# ADR 0011：会话级操作审批模式

- 状态：已接受
- 日期：2026-08-02

## 背景

k-Coder 默认对写入、删除、外部进程和网络工具逐次请求用户批准。连续编辑和验证工作流中，用户有时会明确愿意在当前应用会话内授权全部已注册工具操作，但授权方式不能由模型参数决定，也不能借此绕过工作区、工具和运行时安全边界。

## 决策

运行时提供两种由用户在输入区显式选择的审批模式：

- `ask`：默认模式，风险操作继续进入既有审批等待流程。
- `full_access`：自动批准当前运行时已经注册且通过策略分类的工具操作。

审批模式由 `AppState` 持有，应用启动时始终恢复为 `ask`，不写入持久化设置。活动 Turn 或子智能体存在时禁止切换，主智能体和子智能体在启动时取得同一份模式快照。

`full_access` 只替代逐次用户确认，不扩大 Capability。Schema 校验、路径规范化、工作区逃逸拒绝、Patch 修改前哈希、Hooks、命令超时、取消、输出限制和进程树清理继续执行。每次自动批准仍持久化配对的 `approval_requested` 与 `approval_resolved` 事件，并使用后端生成的 Patch 审阅哈希完成写入授权；模型不能声明或修改审批模式。

## 影响

收益：

- 用户可以在可信工作流中减少重复确认，同时保留明确的可见状态。
- 自动批准操作与手动批准操作共用同一审计和文件事务路径。
- 应用重启后自动回到保守默认值，避免高权限模式被遗忘。

成本与限制：

- `full_access` 不是操作系统沙箱逃逸，也不表示可以访问任意文件或任意网络资源。
- 模式是整个应用会话的运行时设置，而不是单个会话线程的持久属性。
- 切换模式前必须停止活动 Turn 和子智能体。

## 未采用方案

### 只在前端隐藏审批弹窗

未采用，因为后端仍会阻塞等待，界面状态与真实授权行为不一致。

### 在工具参数中加入 `approved` 或 `approvalMode`

未采用，因为模型不能成为自身权限的授权方。

### 持久化完整访问模式

未采用，因为应用重启后无提示地延续高权限状态会扩大误操作风险。
