## 一、为什么「还是不够明显」

深色色调的可见度由三层衰减连乘决定：

```
图像在最终底色里的权重 = (1 − 黑纱) × (1 − 未被「图片可见度」抵消的白纱) × (1 − 面板不透明度)
```

`P10-200` 配平后是 `0.68 × 0.90 × 0.18 = 0.110`（会话区），而浅色色调是 `0.90 × 0.48 = 0.432`——差 4 倍。

更关键的是**图的类型**：`public/chat-background.png` 是一张低频雾状渐变图（`scripts/make-background.cjs`，亮度约 130~250），它的「明显」几乎全部来自**结构量**（图像在面板上的亮度跨度），而不是平均亮度。把跨度和权重一起量出来（真实渲染的逐像素统计）：

| 区域 | 色调 | 图像结构（p95−p5，L\*） | 开/关背景的平均亮度差 ΔL\* |
| --- | --- | --- | --- |
| 会话区 | 深色 | **4.87** | 7.53 |
| 会话区 | 浅色 | 16.84 | 8.01 |
| 侧栏 | 深色 | 2.24 | 16.51 |
| 侧栏 | 浅色 | 8.76 | 3.34 |

深色会话区的结构量只有浅色的 29%，而它的底色均值又和中性的 `#1e1e2e` 只差 15 个 sRGB 单位——这就是「不够明显」的量化形态：**不是图被挡住了，是图的层次被压平了**。

## 二、改动

| 文件 | 改动 |
| --- | --- |
| `src/App.css` | `[data-tone="dark"] .workbench--background::before`：黑纱 `rgba(0,0,0,.32)`→`.16`；`filter: saturate(0.62) brightness(0.98)`→`saturate(0.68) brightness(0.98) contrast(1.08)` |
| `src/App.css` | 深色面板只下调两块最大的面：会话区 `82%`→`72%`、侧栏 `87%`→`78%`；**输入区/标题栏（85%）与设置弹窗（88%）刻意不动** |
| `src/App.css` | 设置页深色预览的 `::before` filter 与 `::after` 黑纱同步到同一组值，保持「预览 = 工作区」的同源合成 |
| `scripts/validate-readability-native.cjs` | 深色背景断言基线 `conversationAlpha 0.82 / sidebarAlpha 0.87` → `0.72 / 0.78` |

三点设计取舍：

1. **为什么加 `contrast(1.08)` 而不是继续提亮度。** 这张图的亮端本来就接近 `#fffffe`，`contrast()` 对它是「亮端裁到白、暗端压深」——结构变明显的同时，暗部反而更暗、更好读。继续提 `brightness()` 只会整体抬亮面板，是纯亏。
2. **为什么只动会话区与侧栏。** 它们是整屏面积最大的两面，也是可见度的主要来源；输入区与标题栏承载整屏最密的文字（草稿、标题），再往下调换来的收益有限，却要先啃掉它们的可读余量。深色面板现在收在 `72% / 78% / 85% / 85%`，跨度与浅色的 `52% / 60% / 54% / 56%` 同量级。
3. **为什么不再靠「压深墨色」换可见度。** 深色面上压深墨色等于抹掉文字（`P10-194` 的根因），所以深色色调只能靠「图更透 + 面板更薄」，代价必须显式记账（见 3.3）。

## 三、真实渲染实测

方法：真实 Edge（`PLAYWRIGHT_CHANNEL=msedge`）+ `tools/ui-harness/ui-harness.html?theme=<id>`（真实组件、真实 `App.css`、mock 宿主）在 1280×820 下渲染，同一布局各拍两张——背景开/关——再做**逐像素**统计：

- 像素由页面内 canvas 解码截图后读取（不引入任何图像库），亮度用 WCAG 相对亮度，颜色用 CIE L\*（感知均匀）；
- 量取时把面板**内容整体 `visibility: hidden`**，剩下的像素就是「半透明面板 + 背景图」的真实合成底色，不会被字形、头像、代码块的最亮点污染；
- 四角**内缩 20px**：面板是 12px 圆角卡片，角外是「没被面板盖住」的原图，会把最坏点带偏（未内缩时最坏点会落在 `#757e7e` 的圆角切口上）；
- 「可见度」= 同布局两张图的逐像素亮度差：均值差代表整体透出量，`p95 − p5` 代表图像结构。

## 五、已知边界

- **未做原生桌面验收**：没有启动隔离 `pnpm tauri dev` + WebView2 CDP 做桌面目视确认，因此不得声称桌面工作流已验证。上述实测来自真实 Edge 渲染的真实组件与真实样式。
- **只实测了 codebuddy/synthwave 之外的主色调分支**：本轮实测覆盖 `data-tone` 的深色与浅色两支，主题取 `dark`（`#1e1e2e`/`#313244`，中性面最亮的一套，属最不利）。`crt-green` / `terminal` / `ember` / `synthwave` 的中性面更暗，同样的面板不透明度**不会**让正文更差；但这四套的 `--color-ink-faint` 相对自身卡片面本就只有约 2.0~2.5:1（`docs/深色主题样式对齐验证.md` §8 已记录的既有缺陷），本轮未一并修。
- 深色色调现在比浅色色调更「吃」自定义图：任意**暗色自定义图**在深色色调下几乎没有可透出的亮度差，这是「用户自选图片 + 自选可见度」的固有代价。
- 面板透明度的选择是**审美判断**：再往下调（例如会话区 68%）会让 `--color-ink-muted` 逼近 4.5:1 的下限，并且整屏开始「发灰」；本轮停在结构量翻倍、次要文字仍有 0.5 以上余量的位置。
- 合成底色里仍含面板 `backdrop-filter: blur(8px)` 的真实效果（本方法完全走真实渲染，不再是上一轮的解析模型近似）。
