# 移动设备设置页「已授权设备」删除入口验证

- 日期：2026-09-17
- 路线图：P10-195
- 用户要求：设置 → 移动设备 → 已授权设备列表「加个删除」。

## 背景：撤销不够用

设备行原本只有「撤销」一个操作，而已撤销的设备**连撤销都没有**——按钮按 `revoked` 隐藏后，那一行变成纯展示，没有任何可用操作。于是列表只增不减：用户换过几台手机之后，历史设备会一直留在设置页。

撤销和删除不是同一件事，本轮把语义拆开：

| 操作 | 数据结果 | 适用场景 |
| --- | --- | --- |
| 撤销（原有） | `revoked = true`，记录**保留**在登记表与设置页 | 设备丢了/暂时不用，但想留着记录便于日后核对 |
| 删除（新增） | 记录连同密钥摘要一起从登记表**移除**，设置页不再展示 | 设备已经不用了，不需要留档 |

删除活跃设备在效果上强于撤销：记录消失后 `authenticate` 会以「unknown device」拒绝，而不是「device was revoked」。

## 改动

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 登记表 | `src-tauri/src/mobile/auth.rs` | `DeviceRegistry::remove`：从 `devices` 里 `retain` 掉记录并落盘，记录不存在时返回 `not_found`（不静默成功） |
| 服务 | `src-tauri/src/mobile/mod.rs` | `MobileService::remove_device`：**先清内存访问令牌，再删记录** |
| 命令 | `src-tauri/src/commands/mobile.rs` | `mobile_remove_device`，泛型到 `R: Runtime` |
| 注册 | `src-tauri/src/lib.rs` | 生产 `generate_handler!` 新增一行 |
| 前端 IPC | `src/api/runtime.ts` | `removeMobileDevice(deviceId)` |
| 界面 | `src/components/MobileSettingsPage.tsx` / `.css` | 设备行新增「删除」按钮 + 二次确认弹窗；撤销图标 `Trash2` → `Ban` |
| 测试 | `src-tauri/tests/mobile_gateway.rs`、`e2e/mobile-settings.spec.ts` | 见下节 |

### 为什么先清令牌再删记录

令牌清理只动内存、不会失败；反过来先删记录的话，一旦落盘失败就会留下「记录已消失、令牌还在」的中间态——那些令牌在 `TokenStore::resolve` 里因为查不到设备而被拒，行为上无害，但会让人误以为删除失败却已经掉线。当前顺序的最坏情况是「设备被踢下线而记录仍在」，用户重试即可，语义更容易解释。

### 界面细节

- 删除按钮**始终显示**（撤销按钮仅在未撤销时显示），这是本轮要解决的核心问题。
- 二次确认弹窗按 `revoked` 分支给出不同后果文案：已撤销的设备提示「删除后这条记录不再出现在列表里，且无法恢复」，活跃设备提示「该设备会立即失去访问权限，需要重新配对才能接入」。
- 弹窗用页面自己的 `.mobile-settings__confirm-backdrop`（`z-index: 100`），而不是全局 `.modal-backdrop`（`z-index: 50`）——设置弹窗本身就是一个 `z-index: 50` 的 backdrop，同级叠放会随 DOM 顺序漂移。
- 确认后**先关弹窗再执行**：失败时页面顶部的错误条必须可见，否则用户面对一个没有任何解释的弹窗只能靠猜。
- 列表下方补了一行说明：「撤销会保留这条记录并立即断开设备，方便日后核对；删除会把记录从列表里彻底移除。」

## 测试覆盖

新增 4 处，逐层递进：

| 测试 | 位置 | 断言 |
| --- | --- | --- |
| `removed_device_disappears_from_registry_and_state_file` | `mobile::auth`（单元） | 删除后内存与**落盘**记录都消失、凭据不再能认证、重新 `load()` 不复活、重复删除返回 `not_found` |
| `removing_a_device_drops_it_from_status_and_invalidates_its_tokens` | `commands::mobile`（mock runtime，走真实命令函数） | 删除后状态快照为空、`tokens.resolve(...)` 失败、重新加载登记表为空、二次调用 `not_found` |
| `removed_device_loses_access_immediately` | `mobile_gateway.rs`（传输层集成） | 按与 `remove_device` 相同顺序操作后，**已认证连接的下一条请求** `unauthorized`、重新握手同样失败、重复删除 `not_found` |
| 删除流程（并入既有用例 `mobile settings page drives gateway, pairing and device control`） | `e2e/mobile-settings.spec.ts` | 取消不产生任何调用；确认后设备行消失、在用计数回落为「1 台在用」；入参为 `{ deviceId }`；**失败分支**显示错误条且记录不被抹掉 |

第 3 项是刻意补的：`revoked_device_loses_access_immediately` 已经守着「撤销后连接立刻失效」，删除比撤销更彻底，如果只测到「记录没了」而没测「已建立的连接会不会留窗口」，就漏掉了最关键的一条。

第 4 项的失败分支用桩实现：真实后端上要造出「记录刚好消失」的竞态才能触发，所以桩在第一次调用时直接抛 `not_found`，断言错误条文案。错误条用 `getByRole("alert")` 定位——页面 toast 是 `role="status"`，两者不冲突。

## 一个覆盖盲区与它的补法

`commands/mobile.rs` 的 mock runtime 测试注册的是**它自己的** `generate_handler!` 列表（第 180 行），而不是 `lib.rs` 里那份生产列表。这意味着**如果只在测试列表里注册、忘了改 `lib.rs`，那套测试照样全绿**，但真实应用里这个命令根本不存在。

本轮改用对**构建产物**取证：在 `src-tauri/target/debug/k-coder.exe` 里查字面量，`mobile_remove_device` 与 `mobile_status` / `mobile_revoke_device` / `mobile_set_capabilities` 一样各命中 1 次，说明生产 `generate_handler!` 确实注册了。

1. **原生桌面路径未验收。** 这是本轮唯一真正的缺口，原因是**环境阻断**，不是代码问题：

   按仓库既有惯例补了隔离宿主配置 `src-tauri/target/mobile-delete-validation.json`（独立 identifier `com.kcoder.validation.mobiledelete`、Vite 1481）与驱动脚本 `scripts/validate-mobile-delete-native.cjs`（走真实 `POST /pair` 完成配对——challenge id/secret 从二维码 URI 的 `#c=<id>.<secret>` fragment 里解析，再由真实 WebView2 点击删除，最后回读 `mobile/state.json` 验证记录确实从磁盘消失）。

   宿主能起来，CDP 也**连通过一次**，但随后稳定失败在 WebView2 的 DevTools 端点：**端口处于 `LISTENING`、TCP 能连上、一个字节都不回**；`curl /json/version` 超时，`chromium.connectOverCDP` 卡在 `<ws preparing> retrieving websocket url`。

   已逐项排除：独立/每次全新的 `WEBVIEW2_USER_DATA_FOLDER`、`--remote-allow-origins=*`、`Host: localhost` 头、IPv6、代理（`--noproxy '*'`）、残留浏览器进程占用端口、前台执行与后台执行。同机自建的 9423 HTTP 服务 `curl` 正常，说明回环本身没有被拦。

   脚本保留在仓库里，头部写明了症状、排除项与复跑步骤，环境恢复后可直接补验。
